# ADR-009: The patient arrives inline with the referral

**Status:** Accepted
**Date:** 2026-08-19
**Decided by:** user (D13 in `docs/PHASE4_PLAN.md`).

## Context

Plan §8's Phase 4 design brief (`docs/UI_DESIGN_BRIEF.md`, Screen 2) has the
ASHA type a new patient's name, age and sex directly into the create-referral
form — no separate "add patient" step, because creating a referral is the
highest-frequency action and the brief requires it to be the shortest path
(handoff §8, plan §8.3).

The server does not support this today. `_apply_create_referral`
(`server/app/sync/push.py`) requires `payload.patient_id` to already exist in
`patient`; there is no `create_patient` operation; and `patient` has no `age`
or `sex` column. An ASHA can create a referral only for one of the four seeded
patients.

This has to be decided now, not deferred into Phase 6, because Phase 6
(`docs/IMPLEMENTATION_PLAN.md` §10) is where **duplicate** patients get
resolved — a probable match between two already-created records. Phase 4 is
where a patient record is first **created**, offline, by a single ASHA with no
directory to search. The two are different problems and the seam between them
has to be placed correctly the first time, because Phase 6 builds directly on
top of whatever Phase 4 leaves behind.

## Decision

`create_referral`'s payload gains `patient_name`, `age`, `sex`, and `phone`
(phone already optional per the brief). `_apply_create_referral` resolves the
patient before writing the referral: look for an existing row with an exact
match on `(normalized_name, village_org_id)`; reuse it if found, otherwise
insert a new `patient` row. Both the resolution and the referral insert (and
its CREATED event) happen in the **same transaction** as the rest of
`apply_operation` — I1 does not carve out an exception for a row this
operation happens to also need.

Migration `0005` adds `patient.age` (integer, nullable) and `patient.sex`
(text, nullable) — nullable because the four Phase 2 seed patients and any
patient created before this phase have neither, and backfilling fictional
values for them would be worse than leaving them null.

The match is deliberately exact, not fuzzy. Fuzzy matching without blocking
first is one of the four things the handoff calls unforgivable
(`docs/HANDOFF_CLAUDE_CODE.md` §5, point 4), and blocking by village plus
phone prefix is exactly the pipeline Phase 6 is scoped to build — building a
smaller, unreviewed version of it here to save a phase would pre-empt that
work rather than prepare for it. Phase 6 replaces this one `SELECT` with its
blocking-and-scoring pipeline at exactly this call site and nowhere else.

## Alternatives considered

| Option | Why not |
|---|---|
| A separate `entity="patient", operation="create_patient"` op, sent before `create_referral` | Pushes ordering and partial-failure handling onto the client: two ops queued offline, only the first one lands, and now there is an orphaned patient with no referral or a referral op that fails against a patient that was never created. `create_referral` already has to name a patient; giving it the data to make one itself removes an entire failure mode rather than handling it. |
| Restrict Phase 4 to the four seeded patients, no new-patient path | No schema or contract change, but Screen 2 becomes a dropdown against a fixed list instead of the form the design specifies, and the strongest demo moment — creating a referral for a patient that did not exist a minute ago, offline — is gone. |
| Fuzzy-match the new patient against existing records at creation time | This is Phase 6's job, done early and without the blocking step the handoff requires before any fuzzy pass. A wrong merge at referral-creation time is worse than a duplicate patient row Phase 6 later reconciles. |

## Consequences

**Makes easy.** Screen 2 can be built exactly as designed — one form, one
submit, works offline. Phase 6 has a single, named call site to replace.

**Makes hard, and the honest cost.** Exact-match-only means two patients with
the same name typed slightly differently in the same village become two rows,
silently, until Phase 6 runs. That is an accepted, temporary duplicate-data
cost, not a correctness bug — nothing downstream trusts patient identity for
anything invariant-bearing before Phase 6 exists to resolve it.

**A second cost.** `patient.age`/`sex` are nullable, so every reader of that
table has to handle `None` from here forward, including any Phase 4 screen
that displays age.

**How the benefit is measured.** An integration test creates two referrals for
patients with the identical `(name, village)` pair and asserts one `patient`
row, not two. A second test creates two referrals for the same name in
different villages and asserts two rows — proving the match is not on name
alone.

## Which invariant this protects

None of I1–I7 directly — patient identity resolution is not one of the
numbered invariants. This decision protects the **blocking-before-fuzzy-match
rule** (`docs/HANDOFF_CLAUDE_CODE.md` §5, point 4: "never fuzzy-match without
blocking first") by explicitly deferring any non-exact matching to Phase 6's
blocked pipeline, rather than building an unblocked shortcut here to save a
phase.
