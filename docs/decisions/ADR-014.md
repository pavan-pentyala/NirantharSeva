# ADR-014: Blocking is by village always; phone narrows only when both records have one

**Status:** Accepted
**Date:** 2026-08-20
**Decided by:** user (D27 in `docs/PHASE6_PLAN.md`).

## Context

`docs/HANDOFF_CLAUDE_CODE.md` §5 lists four things that must not be got
wrong, and the fourth is *"never fuzzy-match without blocking first"* —
unscoped matching across the whole patient table merges two different
people and the error is invisible until someone is treated on the wrong
history. Plan §10.1 gives the blocking key as
`block(village_id=village_id, phone_prefix=phone[:4])`.

That snippet cannot run as written. `patient.phone` is nullable (migration
0003), `create_referral`'s payload treats phone as optional (ADR-009, and
`docs/UI_DESIGN_BRIEF.md`'s Screen 2 marks the field "Optional"), so
`phone[:4]` raises `TypeError` the first time an ASHA leaves it blank —
which, for a woman referred from a village where the household shares one
handset, is the common case rather than the edge case. The design bundle's
own Screen 6 mockup shows precisely this pair: an existing record with a
phone number, a new referral with *"No number given"*, boxed in red as the
field the nurse must weigh.

Guarding the crash naively — skip candidates whose phone prefix does not
match — is worse than the crash, because it fails silently: a patient with
no phone matches no candidate ever, so every phone-less patient becomes a
permanent duplicate, and the pipeline reports high precision precisely
because it stopped trying.

## Decision

Blocking scopes candidates by **village always**, and uses phone only to
narrow, never to exclude:

```sql
WHERE p.village_org_id = :village_org_id
  AND p.merged_into_id IS NULL
  AND (:phone IS NULL OR p.phone IS NULL OR left(p.phone, 4) = left(:phone, 4))
```

Village is the hard boundary and is never relaxed — it is the predicate
that makes the handoff's fourth rule structural rather than aspirational.
Phone is a *refinement*: when both records carry one, a disagreeing prefix
removes the candidate; when either side is missing it, the pair stays in
the candidate set and the fuzzy scorer decides on the name.

`merged_into_id IS NULL` is part of the same predicate rather than a
separate concern: a record already merged away is not a candidate for
anything, and without this clause the same resolved duplicate is
re-suggested to the nurse on every subsequent referral, forever.

Blocking recall — the fraction of true matches that survive this predicate
at all — is reported alongside precision, recall and F1, per plan §10.2.

## Alternatives considered

| Option | Why not |
|---|---|
| Block on village only; ignore phone entirely | Simplest, and it never excludes a true match, so blocking recall is 100% by construction. Rejected because that is exactly what makes it useless as a *reported* number — §10.2's point is that blocking caps achievable recall and the cap must be visible. It also grows the candidate set to every patient in the village, which is the cost blocking exists to avoid. |
| Block on `(village, phone_prefix)` strictly, treating NULL as its own bucket | Every phone-less patient blocks only against other phone-less patients. Tidy, and it does not crash — but a woman registered once with the household phone and once without it can then never be matched to herself, which is the single most likely duplicate shape in this domain. It fails in exactly the case the design chose to illustrate. |
| Block on village, then use phone agreement as a scoring signal instead of a filter | Genuinely defensible, and arguably better matching. Rejected for this project because it changes what "blocking recall" means — with no phone filter there is no phone-driven blocking loss to report, and E3's failure taxonomy loses the ability to attribute an error to the blocking stage specifically. Scoring on phone is also a second scorer to tune, and E3 already sweeps one threshold. |
| Widen blocking to the sub-centre so cross-village duplicates are catchable | Would catch a real duplicate shape — a family that moved between villages. Rejected because it directly weakens the handoff's fourth rule for a case the system has no other defence against, and a cross-village false merge is the specific harm that rule exists to prevent. The gold set instead reports these as blocking losses, honestly, rather than reaching for them. |

## Consequences

**Makes easy.** The pipeline runs on real data without a crash on the most
common input shape. A patient whose phone was recorded once and omitted
once is still matchable. The candidate set stays small in the ordinary case
where both phones are present.

**Makes hard, and the honest cost.** Two genuinely different people in the
same village, with similar names, where at least one has no phone recorded,
are now candidates for each other — the phone can no longer separate them,
and only the name score and the nurse stand between them and a merge. This
is a deliberate trade of precision for recall at the blocking stage, and it
is the reason the review band exists at all. E3's failure taxonomy will
attribute any such error to the scoring/threshold stage, not to blocking,
and that attribution is the point.

**A second cost, and it is the one to state to a panel.** A true duplicate
whose two records sit in *different villages* is unreachable — blocking
rejects the pair before any scorer sees it, and no threshold can recover
it. This is a real ceiling on recall, not a bug, and it is why blocking
recall is reported as its own number rather than folded into recall. A
cohort in which blocking rejects nothing would make that number a
tautology, so `generator/gold_set.py` deliberately emits cross-village and
phone-changed duplicates (D23, `docs/PHASE6_PLAN.md`).

**How the benefit is measured.** Blocking recall in `results/e3_draft/`,
and later E3's own table at three seeds: the fraction of ground-truth
duplicate pairs that survive this predicate. A P6.1 test additionally
asserts that a candidate from another village is never returned, at any
threshold — the assertion that makes the handoff's fourth rule executable
rather than a comment.

## Which invariant this protects

None of I1–I7 — patient identity is not one of the numbered invariants.

It is the executable form of `docs/HANDOFF_CLAUDE_CODE.md` §5's fourth
rule ("never fuzzy-match without blocking first"), which sits alongside
I1–I7 in weight without being numbered. The village clause is the part that
carries that rule; the phone clause is a refinement layered on top and may
be tuned without touching it.
