# ADR-016: One database and one OS process per experiment cell

**Status:** Accepted
**Date:** 2026-08-23
**Decided by:** user (D35 — the isolation strategy); Claude Code for the
process-per-cell mechanism that makes it work, marked below and open to
override.

## Context

Every experiment cell in plan §13 begins "load cohort", runs a timeline
against a `SimulatedClock`, invokes the sweep at intervals, and collects
metrics. Phase 8 runs roughly 63 such cells. Two sections of the plan give
two different, incompatible answers for how a cell is isolated from the one
before it, and neither was written with the other in view.

**§13.1 says a fresh database per cell, obtained by `docker compose down -v
&& up`.** **§12 says the opposite** — a `run_id` column exists so you can
"run eighteen E1 cells without eighteen databases."

Three facts decide it, and none of them were available when either section
was written.

First, **`referral` has no `run_id` column, and that is deliberate.**
Migration `0003`'s own docstring draws the line: `referral_event` and
`sync_conflict` carry `run_id` because they "record something happening
during a specific run"; cache and lookup tables — `referral`, `patient`,
`escalation` — do not. So `run_id` cannot scope the thing E1 actually
measures. `app/domain/escalation.py`'s sweep selects from `referral` by
`current_state` and age; with several cells resident in one database it
would escalate other cells' referrals, and E1's headline number would be
measuring cross-contamination.

Second, **`server_lamport` is a global maximum over the whole
`referral_event` table** (PROGRESS.md "Known problems"; observation 52).
Two cells sharing a database share that ceiling. P7.2 already lost a day to
this in a much milder form, where the contaminating writes were other
*tests* rather than other experiment cells.

Third, **the runner cannot `docker compose down` the container it is
running inside.** §13.1's mechanism forces the runner out onto the host,
which is the one place this project has never run anything (`CLAUDE.md`:
"Everything runs through Docker Compose. Nothing is installed on the
host.").

## Decision

**Each experiment cell gets its own PostgreSQL database, created by `DROP
DATABASE IF EXISTS` / `CREATE DATABASE` against the `postgres` maintenance
database, and is executed by its own short-lived OS process with
`DATABASE_URL` pointed at that database before any `app.*` module is
imported.** Within that process, the runner drives the real FastAPI
application through an in-process ASGI transport rather than a TCP socket.

This supersedes §13.1's container-teardown instruction and §12's
"eighteen cells, one database" claim. `run_id` keeps its existing job —
labelling rows within a run for `request_timing` and event provenance — and
does not become an isolation mechanism.

### Why the process boundary is not optional — the part that was nearly missed

`app/db.py` builds its engine at **import time**:

```python
settings = get_settings()
engine = create_async_engine(settings.database_url, pool_pre_ping=True)
async_session_factory = async_sessionmaker(engine, expire_on_commit=False)
```

and `app/api/sync.py` imports `async_session_factory` as a module-level
name, handing it directly to `handle_push`. It is **not** a FastAPI
dependency. `app.dependency_overrides` can redirect `GET /sync/pull` (which
does use `Depends(get_session)`) and it cannot redirect `POST /sync/push`
at all. An in-process harness that overrode only what FastAPI exposes would
run every cell's writes into whichever database happened to be configured
when the process started, while its reads went where they were told — and
the resulting numbers would look plausible.

Setting `DATABASE_URL` before import and confining a cell to one process
sidesteps this completely, and takes every other import-time global with it:
`get_settings()`'s `lru_cache`, `SLA_SCALE`, `RUN_ID`. **This is exactly
what the existing test suite already does** — `docker compose run --rm -e
DATABASE_URL="...nirantharseva_test" api sh -c "... pytest"` is one process,
one env var, set before import. The harness is not inventing a pattern; it
is reusing the one this repository has always used.

### ADR-015 is not weakened by dropping the socket

D28/ADR-015 requires that a cohort be loaded "by replaying it through
`/sync/push`" so that E4 and E6 measure a code path a real device takes,
rather than a second bulk-insert implementation free to drift from
`app/sync/push.py`. An in-process ASGI transport still executes the real
route, the real `handle_push`, the real receipt claim, the real advisory
lock and the real conflict table. Only the socket is gone.
`tests/integration/test_load_cohort.py` has driven `load()` this way since
P7.1, and `load()`'s `client` parameter exists for precisely this.

## Alternatives considered

| Option | Why not |
|---|---|
| `docker compose down -v && up` per cell (§13.1 literally) | ~60s of container churn per cell on top of the load, before any measurement happens; and the runner would have to be driven from the host, which nothing in this project is. |
| One shared database, cells separated by `run_id` (§12 literally) | Needs a new migration adding `referral.run_id`, and a `run_id` filter inside `app/domain/escalation.py`'s sweep — production correctness-critical code modified for an experiment's benefit, in the week §13 opens by declaring the code frozen. Does nothing about the global `server_lamport` ceiling. |
| Make the session factory a FastAPI dependency so overrides reach the push path | The cleanest-looking fix, and rejected on timing rather than on merit: it edits the transaction boundary that I1 depends on, during the phase whose first sentence is "the code is frozen except for bug fixes." Worth doing in a project that had another month; not worth it in the week before the numbers are generated. |
| Monkeypatch `app.db.async_session_factory` at runtime, stay in one process | Must patch every module that imported the name, not just `app.db`. Patch four of five call sites and the cells silently interleave — a failure with no exception, no failing test, and plausible-looking output. Exactly the class of bug this project's whole discipline exists to avoid. |
| Per-cell schemas (`SET search_path`) instead of per-cell databases | Cheaper than a database, but `search_path` is connection state, and one pooled connection that missed the `SET` writes into the wrong schema. Same silent-failure shape as the monkeypatch, for a saving of well under a second per cell. |

## Consequences

**Makes easy.** A cell is a pure function of (config, seed, cell
parameters) — nothing survives from the previous cell, because the process
that ran it is gone. A crashed cell cannot corrupt its successors. Cells
become trivially parallelisable later if the wall-clock time turns out to
matter, since they share nothing but the Postgres server. Re-running one
failed cell out of sixty-three needs no special path.

**Makes hard, and the honest cost.** Process spawn plus `CREATE DATABASE`
plus `alembic upgrade head` plus `python -m app.seed` is paid per cell,
around 3–6 seconds — cheap, as predicted. **What this ADR did not predict,
and P8.1 found by measuring rather than assuming (`docs/PHASE8_PLAN.md`):
`server/scripts/load_cohort.py::load()` has no "already sent" cursor, so a
stepped-clock loop that calls it once per checkpoint pays a cost that grows
roughly with the *square* of the checkpoint count, not linearly.** A first
measurement at a checkpoint cadence tuned for realism (`LOAD_STEP_HOURS=24`)
came back at 590 seconds for one cell — about 7.4 hours for the full E1
grid. Coarsening the cadence to `LOAD_STEP_HOURS=168` cut it to 89.5
seconds (45 cells ≈ 67 minutes), at the cost of a wider
`state_entered_at` lag documented in `experiments/grid.py`. This is a real
cost this ADR's own estimate missed, not a cost the process-per-cell design
itself introduced — it would apply identically inside a single shared
process. Debugging is a little worse too: a failure inside a child process
needs its output captured and surfaced by the parent rather than raising
into the runner's own traceback, so the runner must not swallow child
stderr.

**A second cost.** The parent runner needs a connection to the `postgres`
maintenance database to create and drop databases, which is a privilege the
application itself never uses. It is a dev-tooling credential in a
Compose-local Postgres, not a production concern, but it is a genuine
difference between how the harness and the app connect, and it belongs in
the report rather than being discovered by a reader.

**How the benefit is measured.** P8.1's exit criteria require that one E1
cell, re-run with the same seed, produces a byte-identical `raw.csv` row,
and that `python -m app.verify_replay` is clean inside a cell's own
database after that cell completes. A shared-state leak between cells would
break the first; a corrupted event log would break the second.

## Which invariant this protects

Primarily **I7** — every experiment result reproducible from a seed and a
config file. Cross-cell contamination is the most likely way I7 fails in
practice, because it produces numbers that are wrong but not obviously
wrong, and it fails *silently*: nothing raises, nothing goes red, and the
tables in Chapter 4 look exactly as they should.

Indirectly **I3** and **I5** — `verify_replay` per cell, and the escalation
sweep operating only on the cohort it was meant to see.
