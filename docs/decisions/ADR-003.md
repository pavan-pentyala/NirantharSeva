# ADR-003: Conflict resolution records both writes and never picks a clinical winner

**Status:** Accepted
**Date:** 2026-08-17
**Decided by:** user (policy mandated by `docs/IMPLEMENTATION_PLAN.md` §6.3);
Claude Code for the two gaps the plan's table left open, marked below.

## Context

NirantharSeva is offline-first. Two health workers can be disconnected at the
same time, each looking at a referral they last synced hours ago, and each can
act correctly on what they can see. When both devices reconnect, the server
receives two operations that disagree about what state the referral was in.

A concrete case, and the one to quote in Chapter 3: an ASHA marks a referral
`IN_TRANSIT` because she has put the patient in an auto to the PHC. At almost
the same moment, offline, the MO at the PHC marks the same referral `ARRIVED`
because the patient walked in on her own. Both are true statements about the
world. Neither worker made a mistake. The referral cannot be in both states.

The constraint that makes this non-obvious is that the losing side is not noise
to be discarded. It is a clinical record of what a named person believed and did
at a named time, and I6 says it is never deleted. A policy that picks a winner
and drops the loser would be simpler and would be wrong — it would erase evidence
that the two sides of a referral had different pictures of the same patient,
which is precisely the failure this project exists to measure.

Phase 1 already resolved concurrent writes for the toy model as a Lamport
last-writer-wins register: highest `(lamport, device_id)` wins. That is the right
policy for an integer field with no meaning. It is the wrong policy for a
patient's referral state.

## Decision

An incoming operation is checked against five conditions **in this order**, and
the first one that matches decides the outcome. `current_state` is the referral's
cached state; `current lamport` is the lamport of the event that produced it,
read from `referral_event` — there is no lamport column on `referral`.

| # | Condition | Status | Event written? | `current_state` changes? | `sync_conflict` row? |
|---|---|---|---|---|---|
| 1 | Actor's role is not in `GUARDS[to_state]` | `rejected` | no | no | no |
| 2 | `to_state not in TRANSITIONS[from_state]` | `rejected` | no | no | no |
| 3 | `from_state == current_state` | `accepted` | yes | yes | no |
| 4 | `from_state != current_state`, incoming lamport **<** current | `accepted_stale` | yes | no | no |
| 5 | `from_state != current_state`, incoming lamport **>** current | `conflict` | yes | no | yes |

Rows 1 and 2 ask whether the operation is coherent **on its own terms**, before
its freshness is considered at all. An ASHA may not write `ARRIVED` no matter how
fresh her clock is (I4), and `CLOSED → IN_TRANSIT` is not a transition that
exists no matter who submits it. These two are the only rows that write nothing.
A rejected operation leaves the event log exactly as it found it, and the
integration tests assert the `referral_event` row count, not merely the returned
status — a `rejected` that quietly appends is invisible until the P3 replay check
disagrees with the cache.

Row 3 is the ordinary path: the device was up to date, the transition is legal,
the role is permitted. Append the event and move the cache in the same
transaction.

Rows 4 and 5 both append the event and both leave `current_state` alone. They
differ only in whether a human is told. Row 4 is a **late** event: the incoming
device had strictly less information than whoever produced the current state, so
its disagreement is explained by the delay and nothing is wrong. It is still
history, it still belongs in the log, and it still cannot move the state
backwards. Row 5 is a **genuine** conflict: the incoming device had seen more
than the device that produced the current state, so its disagreement is not
explained by lag. The system writes a `sync_conflict` row pairing the winning and
losing `op_id`s, changes nothing, and leaves it for a supervisor.

**The system never resolves a genuine conflict automatically.** It records both
writes, keeps the state it already had, and asks a person. That is the decision.

### Gap 1 — equal lamports (the plan's table does not cover it)

Plan §6.3 covers `<` and `>` and is silent on `==`. Equal lamports with different
`from_state` means the two operations are causally concurrent: under the merge
rule, a device that had seen the current event would carry a strictly higher
lamport, so equality proves neither device saw the other.

`docs/PHASE2_PLAN.md` suggested breaking the tie on `device_id`, matching the toy
model's LWW rule. **This ADR does not do that**, and this is the one place the
implementation departs from the approved phase plan.

Equal lamports is not the weakest case of disagreement, it is the strongest — it
is the only case where the two workers provably could not have known about each
other. Rows 4 and 5 both leave `current_state` untouched, so a `device_id`
tiebreak would not be choosing a winner; it would only be choosing whether to
tell a human, based on which device's string sorts higher. That is an arbitrary
reason to stay silent about a real disagreement.

**Decided: `lamport ==` with `from_state != current_state` is row 5 —
`conflict`.** The `device_id` tiebreak stays where it belongs, in the toy
register in `apply_operation`, where some single value genuinely has to be
picked. It is not carried into the referral state machine.

### Gap 2 — operations against a referral that does not exist yet

Also not in the plan's table. Two sub-cases, both `rejected`:

- A `transition` op whose `entity_id` has no `referral` row: `rejected`, reason
  `unknown_referral`. There is no state to compare `from_state` against, so no
  row of the table can be evaluated honestly.
- A `create_referral` op whose `entity_id` already has a `referral` row and whose
  `op_id` is new: `rejected`, reason `already_exists`. A replayed create never
  reaches this — I1's receipt returns the stored answer first. Reaching here
  means two distinct operations claimed the same client-generated UUID, which is
  an error, not a conflict.

## Alternatives considered

| Option | Why not |
|---|---|
| Last-writer-wins on the referral state, as the toy model does | Silently discards one health worker's clinical action and moves the patient's state on the strength of a clock comparison. It also destroys the thing the project measures: how often the two sides of a referral disagree. LWW is right for a meaningless integer and wrong for a patient's state. |
| Reject anything stale — only `from_state == current_state` is ever accepted | Violates I2 and I6. The losing write disappears entirely, so the log no longer contains what the ASHA actually did. It also makes the system unusable offline: any device that syncs second loses all its work. |
| Let the server merge automatically — e.g. take whichever state is further along the workflow | Invents a clinical fact nobody asserted. "Further along" is not a safe heuristic: `ARRIVED` beating `IN_TRANSIT` is plausible, `CLOSED` beating `ESCALATED` is dangerous. A machine choosing between two contradictory clinical claims is exactly what should not happen here. |
| CRDTs — make the state a convergent type so conflicts cannot arise | Frozen scope (handoff §R7), and it does not actually help. A CRDT guarantees convergence, not correctness; it would converge on a state no clinician chose. The problem here is not merging data structures, it is that two people disagree. |
| Block the conflicting operation and make the device re-fetch and retry | There is nobody to retry. The ASHA submitted this hours ago and is in another village. Round-tripping a decision back to a disconnected device is not a resolution, it is a deadlock. |
| Compare `server_time` instead of `lamport` | Device clocks in the field are wrong, sometimes by days, and there is no NTP on a cheap phone with no data. Lamport counters are ordinal and monotone by construction and do not depend on any device telling the truth about the time. |

## Consequences

**Makes easy.** The event log stays a complete and honest record: every action
any worker took is in it, including the ones that changed nothing. The P3
timeline endpoint and the I3 replay property test both fall out of that for free.
Experiment E4 gets a directly countable quantity — `sync_conflict` rows per run —
rather than an inferred one. And the policy is explainable to a non-technical
panel member in one sentence: *the system never decides between two health
workers; it records both and asks a supervisor.*

**Makes hard, and the honest cost.** A `sync_conflict` row is a promise to a
human that goes unkept until Phase 3, when the review UI exists. Between now and
then, conflicts accumulate silently in a table nobody looks at. The referral also
sits at a state that at least one worker believes is wrong, for as long as it
takes a supervisor to look — the system is choosing to be visibly unresolved
rather than invisibly wrong, and that trade is only defensible because a
supervisor exists.

**A second cost.** Row 4 versus row 5 depends entirely on lamport counters being
maintained correctly on every device, through reinstalls and cleared browser
storage. A device that resets its counter to zero has all of its subsequent work
classified as `accepted_stale` and stops raising conflicts it should raise. The
failure is silent. Nothing currently detects it; noting it here so it is a known
hole rather than a surprise.

**A third cost, stated because a panel will find it.** `accepted_stale` and
`conflict` both append an event whose `to_state` is not the state the referral
ends up in. Anyone reading `referral_event` as a straight sequence of state
changes will read it wrong — the log records *claims*, and only the subset
satisfying row 3 moved the cache. The P3 replay implementation must apply the
same five-row table when it recomputes `current_state`, not just take the last
event's `to_state`. This is the single easiest way to break I3.

**How the benefit is measured.** Experiment E4 reports conflict and stale rates
under concurrent offline editing. The count of `sync_conflict` rows against the
count of events accepted at row 4 is the evidence that the distinction between
"late" and "genuinely conflicting" is doing real work and is not a distinction
without a difference.

## Which invariant this protects

- **I4** — a state transition can only be performed by a permitted role. Row 1,
  checked first, is the server-side guard.
- **I6** — a losing write in a conflict is never deleted. Rows 4 and 5 append the
  event; row 5 additionally records the pair in `sync_conflict`.
- **I2** — no accepted operation is silently lost. Only rows 1 and 2 discard
  anything, and both are refusals returned to the client, not losses.
- **I3** — `current_state` stays derivable, because the table is deterministic
  and replaying it over the log reproduces the cache exactly.
