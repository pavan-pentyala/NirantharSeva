# ADR-007: I3 is verified by a full-database replay scan, run as a CLI

**Status:** Accepted
**Date:** 2026-08-18
**Decided by:** user (D11 in `docs/PHASE3_PLAN.md`); Claude Code for the query
shape and the zero-event rule, marked below.

## Context

I3 says a referral's `current_state` is always derivable by replaying its event
log. Until now it has been protected by two things, and neither answers the
question the invariant actually asks.

`server/tests/property/test_referral_replay.py` generates a random legal walk of
at most six transitions, pushes it, and compares the cache to the replayed log.
It is a good test and it samples. It has never looked at a referral it did not
itself create, and it has never looked at more than one at a time.

`server/app/sync/push.py` carries a bare `assert replayed_state == current_state`
inside `_apply_referral_transition`. It fires only on referrals that are being
transitioned right now, so a referral that drifted and was then left alone is
never examined. It is also an `assert`: `python -O` deletes it outright, which
means the tripwire silently disappears in exactly the optimised runs the Phase 8
experiments might use.

So the question "does I3 hold for every referral in this database, right now" has
no answer. Plan §7 requires one — "`current_state` recomputed from events matches
the stored cache, **for every referral**" — but says nothing about what the
artefact is: a script, an endpoint, a test, or a `make` target.

This matters beyond tidiness. Failure mode #5 in plan §15 is a receipt written
outside the effect transaction, which "produces duplicates only under crash
conditions — that is, only in E4, which is the one experiment where it is fatal."
A cache that has drifted from its log is the visible symptom of that class of
bug. E1, E2 and E6 all report closure rates read from `current_state`; if that
cache is untrustworthy, every headline number in the report is untrustworthy with
it. This check is the only place in the plan where that trust is established, and
running it in week 4 rather than week 9 is the difference between a fix and a
catastrophe.

## Decision

The system verifies I3 with a single whole-database replay scan, exposed as a
command-line module — `server/app/verify_replay.py`, run as
`docker compose run --rm api python -m app.verify_replay` — and *not* as an HTTP
endpoint. It reads every referral and every event in one `LEFT JOIN` query
ordered by `(referral.id, referral_event.seq)`, groups the rows per referral in
Python, folds each group with the existing `replay_state`, and reports every
referral whose replayed state differs from its cached `current_state`. The scan
runs inside a `REPEATABLE READ` transaction so a cache updated mid-scan cannot
produce a phantom mismatch, and it deliberately does **not** take
`pg_advisory_xact_lock(4711)` — ADR-002's lock serialises event *appends*, and a
read-only full scan holding it would stall every concurrent push behind itself.

The module exposes `verify_all() -> VerifyReport`, which **returns a report and
neither prints nor exits**. The `__main__` block does the printing and sets the
exit code (0 clean, 1 on any mismatch); a pytest integration test calls the
identical `verify_all()`. That separation is the whole reason the CLI and the
test cannot drift apart, and it mirrors `server/app/seed.py`, where the same
function serves the demo and the test fixtures. The CLI runs in CI's `server` job
**after** `pytest`, so I3 is checked against a database that the full suite has
just written to.

**Claude Code's calls within this decision.** One bulk query rather than one query
per referral: building the scan out of the per-referral fetch is an N+1, which is
two round trips against the current fixture and thousands against Phase 7's
generated cohort — and the cohort is what Phase 8 runs this against. And a
referral with **zero events is reported as a violation, not skipped**:
`replay_state([])` returns `None`, `referral.current_state` is `NOT NULL`, so a
cache asserting a state the log cannot derive is precisely what I3 forbids. It
gets its own `reason` so it is diagnosable rather than merely counted.

## Alternatives considered

| Option | Why not |
|---|---|
| An HTTP admin endpoint (`GET /admin/verify-replay`) | Puts an unbounded whole-table scan on a request path, where a timeout or a connection-pool exhaustion is a production symptom rather than a script that took a while. It also forces a role decision Phase 2 never made — no role in `GUARDS` corresponds to "may audit the database", and inventing one to satisfy a diagnostic is the wrong reason to touch the auth model. Nobody in the domain does this; it is an operator action, and operators have a shell. |
| One query per referral, looping | Correct, and simpler to write. But it is O(referrals) round trips, and this is the check Phase 8 runs against a generated cohort. Choosing the shape that works at fixture size and fails at experiment size is a decision to rewrite it later. |
| The existing property test alone | It samples random walks over referrals it created itself. It cannot see a referral written by the seed, by `kill_api.sh`, by a demo script, or by a bug. "Every referral" is not a property Hypothesis can establish. |
| Keep the `assert` in `push.py` and call it done | Stripped by `python -O`. Only examines referrals currently being transitioned. And an `AssertionError` in a request handler is an unhandled 500 that rolls back a *legitimate* write because of *pre-existing* corruption — which a sync client will then retry forever. |
| Feed `replayed_state` to `decide()` and treat the cache as advisory | Tempting, and wrong. The cache and its event are written in the same transaction, so a divergence between them is a bug, not a race. Reading around the bug hides the only symptom it has. It also changes write-path behaviour during a phase plan §7 explicitly reserves as buffer. |
| Store results in a `replay_check` table with a `run_id`, for report evidence | A new table for output a CLI already prints, and a schema change is on the ask-first list. If Chapter 4 wants the evidence, redirect the CLI's output into `results/` at Phase 8 — plan §12 already commits that directory. |

## Consequences

**Makes easy.** I3 stops being a property that tests sample and becomes one CI
asserts, over whatever data happens to exist, on every push. Because the CI step
runs after `pytest`, the assertion covers everything 168 tests just wrote —
including data written by paths nobody thought to write a replay test for. That
is the highest evidence-per-line change in Phase 3.

**It permits the `assert` in `push.py` to be downgraded, and that is a direct
consequence rather than unrelated tidying.** With a real detector in place, the
write path logs the divergence at ERROR with `referral_id` and `op_id` and
continues with the cache. This is only defensible *because* this ADR exists;
removing the tripwire without building the detector would be a regression.

**Makes hard, and the honest cost.** The scan is not incremental. It reads every
referral and every event, so it is O(events) in time and holds the grouped rows
for one referral in memory at a time. At Phase 7's cohort size this is fine; past
roughly 10⁵ referrals it wants chunking by `referral.id` range, and whoever hits
that owns the change. A second cost: the check runs when someone runs it. It is
not a continuous guarantee, and between two runs the invariant is asserted by the
same transaction discipline that was always protecting it.

**A third cost, specific.** Because a zero-event referral is a violation, any
future code path that creates a `referral` row without appending its `CREATED`
event will fail this check rather than pass it quietly. That is the intent, but it
means the seed and every fixture must append events, not just rows — `seed.py`
already does, and anything new must.

**How the benefit is measured.** The CI step is the measurement: a green
`python -m app.verify_replay` after the suite means I3 held across every referral
the suite produced. The corrupted-cache test measures the detector itself — it
deliberately breaks a cache row and asserts the report catches that exact
referral, so a verifier that silently passes everything cannot itself pass.

## Which invariant this protects

**I3** — a referral's `current_state` is always derivable by replaying its event
log. This is the first artefact in the project that checks I3 as stated, rather
than checking it for a sampled subset.

Indirectly **I1**. A duplicate application would append an event without the
matching state progression, which shows up here as a cache/log divergence. Plan
§15 ranks that failure fifth by likelihood and notes it is fatal in E4
specifically; this scan is the assay that finds it in week 4 instead.
