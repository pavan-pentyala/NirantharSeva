# ADR-012: The dashboard stream authenticates by query-string token

**Status:** Accepted
**Date:** 2026-08-20
**Decided by:** user (D19 in `docs/PHASE5_PLAN.md`).

## Context

Every authenticated endpoint in this project reads a Bearer token from the
`Authorization` header, and the client keeps that token in `localStorage`
(`client/src/api/client.ts`). `get_current_user` re-resolves role and org
from `app_user` on every request rather than trusting the token's claims
(ADR-006).

The browser's `EventSource` — the API plan §9.2 specifies, chosen because
it reconnects on its own — **cannot set request headers.** There is no
option, no flag, no workaround within the API. An SSE endpoint guarded the
way every other endpoint is guarded is simply unreachable from the client
the plan names.

This forces a choice between changing how the stream authenticates and
changing what the stream is built on.

## Decision

`GET /dashboard/stream` accepts its token as a query parameter:
`/dashboard/stream?token=<jwt>`. The token is validated by the same code
path as the header form — same signature check, same `app_user`
re-resolution, same org scoping. Only the *transport* of the credential
differs; nothing about how it is trusted does.

The parameter is accepted **on this endpoint only**. Every other endpoint
continues to require the header, and no shared dependency is loosened to
make this work — the query form is opted into explicitly by the one route
that needs it.

## Alternatives considered

| Option | Why not |
|---|---|
| `fetch()` with a `ReadableStream` body reader instead of `EventSource` | Sends a normal `Authorization` header and puts nothing in the URL — genuinely the cleanest on the security axis. Rejected because it discards `EventSource`'s automatic reconnection, which is the specific thing plan §9.2 chose SSE for ("`EventSource`, which reconnects automatically"). We would hand-roll reconnect, backoff and stream re-establishment — new, fiddly, easy-to-get-subtly-wrong code on the path whose whole job is to survive a flaky connection. Trading tested browser behaviour for hand-written retry logic in a project about resilience is the wrong trade. |
| Cookie-based auth for the stream | Standard, keeps the credential out of the URL, and `EventSource` sends cookies. Rejected because it means the API now has two authentication mechanisms to keep coherent — two places to get expiry, revocation and CSRF exposure right instead of one — and the auth model is explicitly an ask-first, change-carefully area (handoff §2). A second mechanism for one endpoint is a large permanent cost for a narrow gain. |
| A short-lived single-use stream ticket, exchanged over the header API | The rigorous answer: `POST /dashboard/ticket` with the header, receive a 30-second one-shot token, put *that* in the URL. Genuinely better, and the right design for a real deployment. Rejected for this project as disproportionate — it adds an endpoint, a ticket store, an expiry policy and a redemption path to protect synthetic demo data, and none of it is what the case study is about. Named here because it is the obvious follow-up question and the answer should be "considered, scoped out", not silence. |

## Consequences

**Makes easy.** `EventSource` works as plan §9.2 assumed, with its
reconnection behaviour intact and no client-side retry code to write or
test. The server-side auth logic stays single-sourced.

**Makes hard, and the honest cost.** Tokens in URLs leak in ways header
credentials do not: web-server access logs, proxy logs, browser history,
and `Referer` headers on any outbound link from the page. This is a real
weakening, not a theoretical one, and it is accepted here for reasons that
are specific and stated: all data in this system is synthetic by explicit
project scope (`CLAUDE.md`), the deployment is a demo, and the token is
already a short-lived JWT (`JWT_EXPIRE_MINUTES`, default 480) rather than a
long-lived secret. **This decision should not survive contact with real
patient data** — if this system were ever pointed at a real cohort, the
ticket-exchange alternative above is the migration path, and that is why it
is documented rather than dismissed.

**A second cost.** Because the credential is in the URL, the stream URL
itself must never be logged by our own code, and must never be put in a
link, a redirect or an error message. That is a rule a future change can
break silently. `app/instrumentation/timing.py` records `endpoint` for
every request — P5.2 must confirm it records the *path*, not the full URL
with its query string, and a test should pin that.

**How the benefit is measured.** Not measured as a benefit — this is a cost
accepted to keep a dependency-free reconnect. What is verified is the
containment: P5.2 asserts the query token works on `/dashboard/stream` and
that no other endpoint accepts it.

## Which invariant this protects

None of I1–I7 — this is an authentication-transport decision.

It deliberately does **not** weaken ADR-006's rule: the server still
re-resolves role and `org_unit_id` from `app_user` on every request and
never trusts the token's own claims for authorisation. A leaked token
grants exactly what that user already had, for as long as it has left to
live — it does not grant the ability to *claim* a role.
