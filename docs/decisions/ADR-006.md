# ADR-006: The server derives org identity; a device never asserts its own

**Status:** Accepted
**Date:** 2026-08-17
**Decided by:** user

## Context

Phase 2.1 populated `referral.origin_org_id` from the client's operation
payload:

```python
"origin_org_id": op.payload.get("origin_org_id"),
```

That was recorded at the time as a deliberate compromise, not an oversight
(`PROGRESS.md`, "Decisions taken by Claude Code this session"): the P0 auth stub
kept users in `DEV_USERS`, where every user's `org_unit_id` was the placeholder
string `"1"` rather than a real `org_unit` UUID. There was nothing trustworthy
to derive the field from, and nothing yet depended on it being true.

ADR-005 changes that completely. `origin_org_id` is now the column the entire
visibility rule is built on — `WHERE origin_org_id IN (SELECT id FROM subtree)`.
A field the client controls has become the security boundary. A device that
writes `origin_org_id` belonging to another village places its referral inside
that village's subtree, and every scoping query in the system will faithfully
honour the lie.

There is a second, separate hole in the same area. P2.1 enforces I4 — a
transition can only be performed by a permitted **role** — but nothing checks
whether the actor has any relationship to the referral being transitioned. An
ASHA in Village A holds a valid token with role `ASHA`, and `GUARDS[CLOSED]`
contains `ASHA`, so she may close Village B's referral. The role guard passes.
The conflict table passes. The event is appended and the state moves. She cannot
*see* that referral after ADR-005, but she can still change it.

The project has already solved this exact class of problem once. P2.1's
`actor_role` comes from the server-verified JWT claim and never from the
payload, with the reasoning recorded in the code: "a device cannot be trusted to
name its own role."

## Decision

**The same rule now applies to organisation and to user identity.**

`origin_org_id` and `origin_user_id` are taken from the authenticated identity.
Any `origin_org_id` or `origin_user_id` present in an operation payload is
**ignored** — not validated and then used, and not treated as an error. A
referral is created in the org unit of whoever created it, by definition rather
than by assertion. When such a key is present and disagrees, the server logs a
WARN carrying the `op_id` and proceeds; **it does not reject the op.** Rejecting
would turn any stale client into a data-loss path — an operation composed before
the upgrade and sitting in an offline outbox for a day would be discarded on
arrival — and since the server value is authoritative either way, ignoring costs
nothing and drops nothing.

`target_org_id` continues to come from the payload. It is a clinical routing
choice the device legitimately makes, and per ADR-005 it is not a visibility
input. The asymmetry is deliberate: fields that decide **who can see this** are
server-derived; fields that describe **where the patient is being sent** are the
device's to state.

`actor_user_id` on `referral_event` is likewise resolved from the authenticated
identity, closing the gap where P2.1 wrote `NULL` because `app_user` had no rows.

**The database, not the token, is authoritative for role and org.** `sub`
remains the username and the JWT claim shape is unchanged, but
`get_current_user` resolves `sub` to the `app_user` row on each authenticated
request and uses that row's `role` and `org_unit_id`. The token's matching
claims stay in place to satisfy the §6.4 contract; they are not what the server
acts on. Two reasons: a token embedding an org id is an eight-hour stale
snapshot of a value that, after ADR-005, *is* the confidentiality boundary — a
user moved between units keeps their old visibility until expiry, and a disabled
user keeps everything. And the push path needs the lookup anyway to populate
`actor_user_id`, so on that path making it authoritative costs nothing extra.

**A transition against a referral outside the actor's subtree is `rejected`,
with reason `outside_org_scope`.**

This check runs **before** ADR-003's five-row conflict table, alongside rows 1
and 2 rather than after them. The ordering follows ADR-003's own principle: rows
1 and 2 ask whether the operation is coherent on its own terms before its
freshness is considered. "Does this actor have any authority over this referral"
is that same kind of question, and it must be answered before the system starts
reasoning about lamport counters. Like rows 1 and 2, it writes no event.

## Alternatives considered

| Option | Why not |
|---|---|
| Keep trusting the payload's `origin_org_id` | Makes ADR-005 decorative. Every scoping query would be correct, well-tested, and enforcing a boundary the client draws for itself. This is the option that looks like it works and does not. |
| Accept the payload value but validate it is inside the actor's subtree | Produces an identical outcome to deriving it, since the only value that survives validation for an ASHA is her own village — but costs a validation path, an error case, and a permanent invitation for "validated" to erode into "trusted" the next time someone needs a special case. Deriving it has no such failure mode because the field is never read. |
| Derive the org but leave transitions unscoped | Closes the read hole and leaves the write hole. An ASHA could still close another village's referral — she just could not see it first. This is the obvious question a panel asks after being shown the scoping demo, and "we only scoped reads" is not an answer. |
| Enforce write scope in the read layer, by making clients fetch before writing | Meaningless offline. The device has been disconnected for hours and is replaying an outbox; there is no fetch to gate on, and the server must decide on the operation alone. |
| Put `org_unit_id` in the payload but sign it | Reinventing the JWT, which already carries a signed `org_unit_id` claim. |
| Add an `org_unit_id` column to the op contract | An API contract change that buys nothing — the server already knows the answer more reliably than the client does. |
| **Reject** the op when the payload claims a different `origin_org_id`, rather than ignoring it | Turns every stale client into a data-loss path. An op composed before the upgrade and queued offline for a day would be thrown away on arrival, which is precisely the failure the outbox exists to prevent. The server value wins either way, so ignoring plus a WARN loses no information and destroys no work. |
| Add a `user_id` claim to the JWT instead of resolving `sub` per request | Makes the token an eight-hour stale snapshot of org membership, which after ADR-005 is the confidentiality boundary itself: a moved user keeps their old scope until expiry and a disabled user keeps everything. It is also the JWT contract change the phase plan promised not to make. The chosen alternative costs one indexed lookup per authenticated request. |
| Let `outside_org_scope` append the event and simply not move `current_state` | Contradicts ADR-003's rule that only rows 3–5 append. A refusal is not history — the actor was never entitled to act on this referral, so there is no clinical claim to preserve — and it would invalidate the row-count assertions P2.1 already relies on. |
| Backfill existing `NULL` `origin_org_id` rows to a default org, instead of requiring `docker compose down -v` | Fabricates a security-relevant fact: an org membership for a referral nobody can attribute, invented to make a migration convenient. All data here is synthetic by explicit project choice, so the wipe costs nothing real. `0004` pre-checks for NULLs and fails with an error naming the wipe, rather than emitting a bare constraint violation. |

## Consequences

**Makes easy.** ADR-005's filter becomes meaningful, because the column it reads
is now a server-controlled fact rather than a client-supplied string. The two
ADRs only work as a pair: neither is sufficient alone, and this one is the
reason the other one is not theatre. `actor_user_id` becomes reliably populated,
which is what the P3 timeline endpoint needs to answer "who did this" and what
ADR-004's envelope already advertises in its example payload.

**Makes hard, and the honest cost.** A referral can now only be created in the
creator's own org unit. There is no mechanism for a legitimate cross-org create,
and if the workflow ever needs one — a visiting ANM raising a referral on behalf
of a village she is not posted to — it needs a new, explicit mechanism rather
than a payload field. That is the right trade for a system where the alternative
is an unenforceable boundary, but it is a real constraint and it is worth
saying before someone discovers it at P6.

**A second cost, specific and worth knowing.** When an ANM creates a referral,
its origin is the **sub-centre**, not the village the patient lives in. The ANM
is posted to the sub-centre, so that is her org unit and that is where the
referral lands. Under subtree descent this is still visible to her and to
everyone above; it is *not* visible to the ASHA in the village below, because
visibility descends and the referral sits above her. Nothing in D4's fixture or
Phase 2's tests depends on the ASHA seeing it, but this is a genuine modelling
consequence and P6/P7 should decide deliberately whether `patient.village_org_id`
rather than the creator's unit is the better origin for that case.

**A third cost.** One additional indexed lookup per authenticated request, to
resolve `sub` to the `app_user` row. It adds no second transaction and no new
failure mode, but every request now touches `app_user`, which becomes a
sync-path dependency it was not before. It is unmeasured; if E5's write-latency
numbers move, this is the first thing to look at.

**A fourth cost, and the one most likely to bite.** `handle_push`'s trailing
`actor_role: str` parameter has to become a richer actor value — user id, role
and org unit together. That signature reaches `app/api/sync.py`, which is
obviously auth-adjacent, and also
`server/tests/property/test_referral_replay.py`, which calls `handle_push`
directly with `Role.ASHA.value` and never touches HTTP, a login, or a JWT. **A
test that contains no reference to authentication is part of this change's blast
radius**, which is exactly the kind of coupling that gets missed. The actor type
belongs in `app/domain/`, not `app/api/` — putting it in the API layer would
make `app/sync/` import from `app/api/`, inverting the dependency.

**A fifth cost.** The client can no longer predict which org a referral will
land in, so any Phase 4 optimistic UI must render the server's answer rather
than its own guess for that field.

**How the benefit is measured.** Two tests, both in P2.2's table: a
`create_referral` whose payload carries a foreign `origin_org_id` lands in the
authenticated user's org and not the asserted one; and a transition against a
referral outside the actor's subtree returns `rejected` and appends no event —
asserted by row count, per trap #4, not by returned status alone.

## Which invariant this protects

**I4** — a state transition can only be performed by a permitted role, here
extended from *which role* to *whether this actor has authority over this
referral at all*. Plan §6.4 implies the extension without stating it; this ADR
states it.

Also the integrity of **ADR-005**. That decision protects the §6.4 data-leak
rule, and it protects nothing at all without this one.
