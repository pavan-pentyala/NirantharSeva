# ADR-011: Escalations cross the process boundary by Postgres LISTEN/NOTIFY

**Status:** Accepted
**Date:** 2026-08-20
**Decided by:** user (D18 in `docs/PHASE5_PLAN.md`).

## Context

`docs/IMPLEMENTATION_PLAN.md` §9.2 sketches the SSE endpoint as
`escalation_bus.subscribe(scope=user.org_subtree)` — an in-process
publish/subscribe object the sweep pushes into and the HTTP handler reads
from.

That cannot work here, and the reason is a deliberate earlier decision, not
an oversight in this phase. The escalation sweep runs in the **scheduler**
container; the SSE endpoint runs in the **api** container. Plan §2.3
separates them so the scheduler can be killed independently, and experiment
E4's fault injection depends on exactly that separation. Two processes, two
memory spaces: an in-process bus in the API is structurally incapable of
observing a row the scheduler wrote.

So Phase 5 needs a transport between the process that detects a breach and
the process holding the browser's open connection — chosen without adding a
broker to a stack that has deliberately stayed small, and without
collapsing the process separation E4 needs.

## Decision

The scheduler issues `NOTIFY nirantharseva_escalation` after the
transaction that inserts an `escalation` row commits. The API holds a
dedicated `LISTEN` connection and, on each notification, wakes every
connected SSE subscriber.

A notification is treated as **a signal that something changed, not as the
changed data**. Each subscriber responds by re-running its own org-scoped
open-escalations query and emitting the result. Nothing security-relevant
travels in the notification payload, and no subscriber ever filters another
subscriber's rows in Python — the `SUBTREE_CTE` predicate stays inside SQL,
where ADR-005 requires it.

## Alternatives considered

| Option | Why not |
|---|---|
| The SSE endpoint polls the `escalation` table on a timer | Simplest possible thing, and genuinely tempting. Rejected because the polling interval becomes a floor on the demo's headline moment — plan §9.3's whole point is a breach appearing *now*, and "up to N seconds late, every time" is a visibly worse demo. It also puts a permanent recurring query on the database for an event that is rare by nature. |
| Move the sweep into the API process so the in-process bus works as sketched | Makes §9.2 correct as written, at the cost of deleting the scheduler/API separation plan §2.3 mandates and E4's kill-the-scheduler fault test exercises. Trading a real experiment for a simpler wiring diagram is the wrong direction. |
| Add Redis (or any broker) as a pub/sub backbone | The textbook answer, and overwhelming here. It is a new service, a new dependency, a new failure mode and a new thing to explain to a panel, to move one rare message between two processes that already share a database connection pool. |
| Have the scheduler POST to an internal API endpoint | No new infrastructure, but it inverts the dependency — the scheduler would need to know the API's address, authenticate to it, and handle its own retries when the API is the thing being killed in E4. The database is already the shared substrate; routing through HTTP adds a hop that can fail independently. |

## Consequences

**Makes easy.** Sub-second delivery with no polling and no new service. The
sweep stays exactly where plan §2.3 wants it. Because the notification
carries no data, adding fields to what the dashboard shows later needs no
change to the transport at all — only to the query each subscriber already
runs.

**Makes hard, and the honest cost.** `LISTEN`/`NOTIFY` delivers
at-most-once with no persistence: a notification issued while the API is
down is simply gone. The dashboard therefore cannot treat the stream as the
source of truth. It must fetch the current open-escalation list on connect
and on every reconnect, and treat notifications purely as "refresh now"
prompts. That is a real constraint on the client, and P5.2's
reconnect exit criterion exists to prove it was respected. The upside of
the same property: a missed notification self-heals on the next one, or on
the next reconnect, rather than leaving a permanently wrong screen.

**A second cost.** The `LISTEN` connection is held outside SQLAlchemy's
pool for the API process's lifetime — one long-lived connection that the
pool does not manage and that must be re-established if the database
restarts. Small, but it is a connection whose lifecycle is now hand-written
rather than inherited.

**A third cost.** `NOTIFY` fires on commit, so a subscriber can be woken by
a transaction whose effects it then re-queries and finds nothing new in —
harmless, but it means "notification count" and "escalation count" are not
the same number, and any future metric must not assume they are.

**How the benefit is measured.** P5.2's headline exit criterion is the
measurement: a Playwright test opens the stream, triggers a breach, and
asserts the row arrives on the already-open connection with no refresh and
no polling interval to wait out.

## Which invariant this protects

None of I1–I7 directly — this is a transport decision on the read path.

It does protect **ADR-005's scoping rule** by construction: because the
notification carries no rows, every subscriber's data still comes from a
query whose `WHERE` clause contains the subtree predicate, and there is no
code path where one supervisor's escalations could be filtered out of
another's stream in application code.
