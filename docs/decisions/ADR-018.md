# ADR-018: Deployment-ready configuration, not a deployed instance

**Status:** Accepted
**Date:** 2026-08-24
**Decided by:** user (D43)

## Context

D41 (`docs/PHASE8_PLAN.md`) resolved a contradiction between the phase map
and §14 by moving deployment out of Phase 8 and into Phase 9. That settled
*when* deployment is considered. It did not settle *whether* a deployed
instance is actually a deliverable, and §14 is more ambivalent about that
than the phase map's bare "deploy" suggests:

> **Primary demo path is local `docker compose up`.** Free-tier hosts
> cold-start, and a spinner during a graded review is a bad minute.
> Deployed URL is secondary; the recorded two-minute clip is your third
> fallback. Have all three.

So the plan simultaneously ranks a deployed URL *second*, gives a concrete
reason to distrust it in the setting that matters (a graded review), and
then asks for all three anyway.

Four facts about *this* stack decide it, and none of them were in view when
§14 was written.

**This is a four-service stack, not a web app.** `docker-compose.yml` runs
`db` (PostgreSQL 16), `api` (FastAPI/uvicorn), `scheduler` (a *second*,
separate Python process running APScheduler), and `client` (Vite). Plan
§2.3 made the scheduler a separate process deliberately, so E4's fault
injection could kill it independently of the API. Most free tiers give one
always-on web service; a second continuously-running background process is
either a paid add-on or not offered.

**The headline demo feature is a long-lived SSE connection.** ADR-011 and
ADR-012's whole point — the twenty seconds §8 says a panel will remember —
is a breached SLA appearing on Screen 4 with no page refresh, over
`GET /dashboard/stream`. Free-tier proxies frequently buffer or time out
long-lived responses, and a buffered SSE stream fails in exactly the way
that is hardest to diagnose live: everything looks fine until the moment
the demo depends on it.

**Escalation is time-driven, so a sleeping instance has nothing to show.**
The scheduler must have been running *before* the demo for a breach to
exist to display. A host that sleeps an idle service, then cold-starts it
on the first request, produces an empty dashboard at precisely the moment
someone is watching — the failure §14 already warned about, made worse by
this system's dependence on elapsed time.

**Nothing in the project's evidence depends on a deployed URL.** Every
experiment result (E1–E6), every fault-injection row, every screenshot and
every test was produced against local Compose. A deployed instance would
demonstrate operability, not correctness — and operability is the one claim
this project has the least evidence for either way.

## Decision

**Phase 9 ships deployment-ready configuration and documented deployment
steps. It does not create, operate, or depend on a deployed instance.**
Local `docker compose up` remains the primary demo path, per §14, and the
recorded clip remains the fallback.

"Deployment-ready" is a concrete artifact, not a claim. It means a
production Compose configuration that differs from the development one in
every way a real deployment would require:

- no source bind-mounts (the image is the artifact, not the host directory)
- no `--reload`, no Vite dev server — the client is served as a built,
  static bundle
- the database port is not published to the host
- CORS restricted to a configured origin instead of `*` (this also closes
  the one deployment-shaped item deferred from the pre-Phase-9 audit)
- every secret supplied by environment variable with **no development
  default** — a missing `JWT_SECRET` must fail loudly at startup rather
  than silently falling back to `dev-secret-change-for-anything-real`

And it must be **verified to actually start and serve**, not merely
written. An unverified production config is a claim; a config that has been
brought up and had its health endpoint answered is an artifact.

## Alternatives considered

| Option | Why not |
|---|---|
| Actually deploy to a free tier (Render/Fly/Railway) | The four facts above, in week 10, on the deliverable with the least slack. The scheduler alone needs a second always-on process; SSE needs an unbuffered long-lived connection; time-driven escalation needs the service never to sleep. Each is individually solvable and collectively a multi-day detour away from the demo path that already works. |
| Skip deployment entirely | Cheapest, and leaves "could this be deployed?" answered only by assertion. The gap is small but real: a panel asking it would get a shrug, when a verified production config answers it in one sentence and costs a fraction of a day. |
| Deploy only the API, demo the client locally against it | Halves the hosting problem and doubles the demo's failure modes — now the demo depends on a network round trip to a cold-starting host *and* on CORS being right across two origins, live. Strictly worse than local for the thing that is being graded. |
| Write the production config but do not verify it starts | The difference between an artifact and a claim, for perhaps twenty minutes of work. Rejected on exactly the same reasoning the rest of this project applies to unverified test assertions. |

## Consequences

**Makes easy.** The demo path stays the one that has been exercised
continuously since Phase 3 — no new failure mode is introduced in the last
week. "Is it deployable?" gets a concrete answer (a file, and the steps)
rather than an opinion. The CORS wildcard, deferred from the pre-Phase-9
audit specifically because a real deployment target would decide its value,
gets closed here instead of drifting.

**Makes hard, and the honest cost.** The project will end with no evidence
of running anywhere but a development machine. That is a real limitation
and belongs in the report's own limitations section, stated plainly rather
than left for a reader to notice: *no production deployment was performed;
the system has been exercised only under local Compose, and claims about
its behaviour under real hosting are therefore untested.* The production
Compose file is checked to start; it is not checked under load, over a real
network, behind a real proxy, or against a managed Postgres.

**A second cost.** "Deployment-ready" is a weaker claim than it sounds and
should not be oversold. A config that starts locally in production mode has
not proven anything about a specific host's proxy behaviour, TLS
termination, or connection limits — the three things most likely to break
SSE. The report should say what was verified (it starts, it serves, secrets
are externalised) and not imply more.

## Which invariant this protects

None directly — this is a scope and delivery decision, not a correctness
one. Indirectly it protects the **demo**, which §14 treats as a primary
deliverable in its own right, by refusing to introduce an untested
dependency into the one path that has been reliable all project.
