# ADR-005: Visibility is the org subtree, applied identically at every read site

**Status:** Accepted
**Date:** 2026-08-17
**Decided by:** user (policy mandated by `docs/IMPLEMENTATION_PLAN.md` §6.4);
Claude Code for the three points §6.4 left open, marked below.

## Context

NirantharSeva's org tree runs Village → Sub-centre → PHC → CHC → District
Hospital (`docs/DOMAIN_PRIMER.md`). A user sees their own unit and everything
below it, never sideways. An ASHA in Village A must not see a referral from
Village B, even though both hang off the same sub-centre.

Plan §6.4 states the rule and gives a recursive CTE, then adds one warning:
"Apply the same scoping to `/sync/pull`. A pull that ignores scope is a data
leak, and it is easy to miss because the UI looks correct." `docs/PHASE2_PLAN.md`
repeats it as trap #1, "the single most consequential thing in Phase 2."

Three things make this harder than §6.4's one-line CTE suggests, and none of
them are addressed there.

First, **`/sync/pull` is no longer a single query.** ADR-004 made it a
`UNION ALL` across `toy_event` and `referral_event` sharing one cursor. That
ADR's own "second cost" paragraph predicted exactly this problem: the scoping
filter "has to be applied to every branch of that union independently — a
scoping predicate applied to the outer query only, or to one branch only, is
exactly the data leak plan §6.4 warns about, and it is easier to write by
accident once the query has more than one `FROM`."

Second, **`referral_event` has no org column at all.** Plan §6.1's schema gives
it `referral_id` and nothing organisational, so scoping events is not a `WHERE`
on the event table — it needs a join back to `referral`.

Third, **`toy_event` has no org column and no possible one.** D1 keeps the toy
model alive until Phase 4 because Phase 1's two Playwright fault tests are
experiment E4's evidence and need a screen to click, which referrals will not
have until P4. Those tests pull toy events. Whatever scoping does to the toy
branch, it must not break them.

## Decision

One recursive CTE, in `app/api/scoping.py`, used by every read site. Nothing
re-implements it locally.

```sql
WITH RECURSIVE subtree AS (
  SELECT id FROM org_unit WHERE id = :root
  UNION ALL SELECT o.id FROM org_unit o JOIN subtree s ON o.parent_id = s.id)
```

`:root` is the authenticated user's `org_unit_id` claim. Three call sites:
`GET /referrals`, `GET /referrals/{id}`, and `GET /sync/pull`.

**Referral events scope through a join, not a column.** The pull's referral
branch becomes `JOIN referral r ON r.id = referral_event.referral_id` filtered
on `r.origin_org_id IN (SELECT id FROM subtree)`. There is deliberately no
denormalised copy of the org on the event row.

**The predicate goes inside each branch of the `UNION ALL`, before the
`LIMIT`** — never applied in Python after the page comes back. This is not a
style preference, and the failure it prevents is worse than under-paging.
`handle_pull` ends with:

```python
cursor = events[-1].seq if events else since
```

A page of 500 rows that filters down to zero in Python leaves `cursor` at
`since` and `has_more` false. The client is told there is nothing more, and its
cursor has not moved — so the next pull asks the identical question, gets the
identical answer, and the client **stops receiving events permanently**. It is
silent, it survives restarts, and no single-user test reproduces it.

Filtering inside the query keeps both quantities honest: the page contains
`limit` *visible* events, and the cursor advances past invisible ones
deliberately and permanently, because they will never become visible.

**Outside the subtree returns 404, not 403.** A 403 confirms that the referral
exists, which is itself the leak.

### Point 1 — `target_org_id` deliberately does not participate

§6.4's CTE filters `origin_org_id` and never mentions `target_org_id`. That is
correct, and the reason is worth recording rather than leaving as an omission.

Referrals travel **up** the tree. A referral raised in Village A targeting PHC
Ramnagar has an origin that is already inside the PHC's subtree, so the
receiving MO sees it by ordinary subtree descent. Filtering on origin alone is
sufficient for every referral the workflow actually produces, and adding
`target_org_id` to the predicate would widen visibility without being needed.

**The cost, stated plainly:** a lateral referral — one whose target is not an
ancestor of its origin, say Village A to a PHC in a different block — would be
invisible to the facility receiving it. No such referral is reachable in D4's
fixture, and nothing in Phase 2 can create one. If a later phase introduces
cross-branch referral, this rule must be revisited, and this ADR superseded.

### Point 2 — the toy branch is deliberately unscoped

Toy events remain visible to every authenticated user. `toy_event` has no org
column, carries no patient data, and models nothing real; it is synthetic
scaffolding that exists so Phase 1's distributed-systems bugs could be debugged
in isolation, and D1 drops it entirely at Phase 4.

Scoping it would mean either inventing an org concept for a table scheduled for
deletion, or excluding toy events from pull — which breaks both Playwright fault
tests immediately, and those tests are E4's evidence.

**This is a time-boxed exception with a defined end.** It disappears when the
Phase 4 migration drops `toy_event`. Until then, "every authenticated user can
read every toy event" is a true statement about this system, and the honest
answer to a panel asking about it is that the toy model contains nothing worth
protecting and is already scheduled for removal.

**This decision supersedes plan §6.4's unqualified sentence** "Apply the same
scoping to `/sync/pull`." The referral branch is scoped; the toy branch is not.

#### Where this appears to contradict ADR-004, and why it does not

ADR-004 states that a scoping predicate "applied to the outer query only, **or
to one branch only**, is exactly the data leak plan §6.4 warns about." This
decision scopes one branch only. That is a real tension and it is the most
probeable seam in the Phase 2 document set, so it is answered here rather than
left for someone to notice.

ADR-004 wrote that sentence while reasoning about a union whose branches all
carry org-bearing data — the case it was actually looking ahead to was P6, when
patient events join the stream. Under that assumption, scoping one branch and
not the other leaks the unscoped branch's rows, and the warning is exactly
right.

`toy_event` breaks the assumption rather than the conclusion. The leak ADR-004
names is a **referral** leak — one health worker seeing another village's
patient. There is no referral data, no patient data, no user and no org anywhere
in the toy branch; it is an integer keyed by a client-generated UUID. Leaving it
unscoped does not leak the thing the warning is about, because that thing is not
in there.

**The half of ADR-004's warning that still binds in full is the outer-query
half.** Applying the predicate to the outer query instead of the referral branch
remains exactly the bug it describes, and it is now trap #7 in the phase plan.
ADR-004 is Accepted and is not edited; this paragraph is the record of the
qualification.

There is one useful accident worth recording, though it must not be relied on:
because the toy branch is deliberately unscoped, an implementation that wrongly
applies the predicate to the *outer* query would also drop every toy row, and
the two Playwright fault tests would fail loudly. The wrong implementation
breaks noisily instead of leaking quietly. That is a property of this design,
not a substitute for reviewing the SQL.

### Point 3 — a `NULL` origin makes the data-leak test pass for the wrong reason

`origin_org_id IN (SELECT id FROM subtree)` is never true when the column is
`NULL`. A referral with no origin is therefore invisible to every user including
the person who created it. It fails closed, not open, which is the safer
direction — but it fails *silently*, and it does something worse than hide data.

**It makes the most important test in Phase 2 pass vacuously.** Every referral
written during P2.1 has `origin_org_id IS NULL`. Run the leak test against that
data and "`asha_a` cannot see Village B's referral" goes green — because
`asha_a` cannot see *anything*, and neither can anyone else. The test reports
success while proving nothing at all.

Two things follow, and both are part of this decision rather than unrelated
housekeeping:

- Migration `0004` sets `origin_org_id NOT NULL`, so the state cannot exist.
  **That constraint is what makes the leak test meaningful**, which is the real
  argument for it — integrity and tidiness are secondary.
- The leak test must assert the **positive case in the same test**: `asha_a`
  sees her own village's referral *and* does not see Village B's. A test that
  only asserts absence cannot distinguish "correctly scoped" from "completely
  broken."

## Alternatives considered

| Option | Why not |
|---|---|
| Filter the pull in Python, after fetching the page | Breaks `has_more` and the cursor together: the client is handed a cursor that has advanced past events it never received and will never request again. That is ADR-002's gap-free guarantee destroyed at the application layer after the database went to some trouble to provide it. |
| Denormalise `origin_org_id` onto `referral_event` so pull needs no join | Creates a second copy of the field the security boundary depends on, which must be kept in sync with the first forever. This is I3's lesson — a cached copy of a derived fact drifts, and here the drift is a data leak rather than a wrong screen. |
| Apply the scoping predicate once, to the outer query of the union | Exactly the failure ADR-004 warned about. Postgres will accept it, the tests pass if they only check the referral branch, and the leak is invisible until someone reads the SQL. |
| Return 403 for a referral outside the subtree | Confirms the referral exists. "You may not see referral X" and "referral X does not exist" must be indistinguishable to the caller, which means 404 for both. |
| Scope by `target_org_id` as well as `origin_org_id` | Widens visibility to solve a problem Phase 2 cannot produce. See Point 1 — deferred deliberately, with the limitation recorded rather than hidden. |
| Give `toy_event` an org column and scope it uniformly | Schema work on a table being deleted at P4, on a model D1 froze. Uniformity for its own sake, at the cost of touching frozen code. |
| Materialise the subtree as a Python list of ids and filter with `IN (...)` | A second round trip, a silent truncation risk as the tree grows, and — worse — it moves the security predicate out of the database into application code, where a later refactor can drop it without any query visibly changing. |
| Postgres row-level security | Genuinely stronger, and it loses on the connection model rather than on merit. The app uses one pooled service role, so RLS needs a per-request `SET LOCAL` of a session variable inside the same transaction that already holds ADR-002's advisory lock — a new failure mode adjacent to the most delicate code in the system, introduced during a phase that is already re-cutting auth. Named here because it is what a production system would do, and because "why not RLS?" is a fair question. |

## Consequences

**Makes easy.** One helper, one definition of visibility, three call sites — the
rule is auditable by reading a single function rather than by trusting three
queries to agree. Adding a fourth read site later (P3's timeline endpoint, P5's
dashboard) is a call to the same helper. The 404 convention means the read API
needs no separate "does this exist" branch.

**Makes hard, and the honest cost.** Every new query that touches referrals is
now a place the filter can be forgotten, and forgetting it produces no error,
no failing test unless one is written for that specific endpoint, and no visible
symptom. The helper reduces the chance but cannot remove it; only a test per
endpoint can, which is why the P2.2 test table has a scoping row per call site.

**A second cost.** `referral.origin_org_id` has no index today, so the filter is
a sequential scan on every read. Migration `0004` adds one. The cost of the
recursive CTE itself on a deep tree is not measured yet; E5 reports read latency
and is where this shows up if it matters.

**A third cost, stated because it is a real hole.** A user whose org unit
changes — transferred to another sub-centre — has a pull cursor that has already
advanced past events they can now legitimately see. They will never receive
them, because the cursor only moves forward. Nobody changes org in Phase 2 and
nothing in the system supports it, so this is theoretical today. It stops being
theoretical the moment an admin screen can move a user, and whoever builds that
screen owns a cursor reset.

**A fourth cost.** Because the toy branch is unscoped, `/sync/pull` currently has
two different security postures in one response. That is defensible only while
the toy model is worthless and short-lived. If toy outlives Phase 4 for any
reason, this ADR must be revisited rather than quietly relied upon.

**How the benefit is measured.** The data-leak integration tests are the
evidence: `asha_a` pulling and receiving zero Village B events, and the same
check at three tree levels. A passing test that `asha_a` cannot see Village B
via `/sync/pull` is the single most load-bearing test in Phase 2.

## Which invariant this protects

Primarily the org-scoping rule of plan §6.4, which is not numbered as an
invariant but is treated as one by `docs/DOMAIN_PRIMER.md`: "a pull that ignores
it is a data leak that the UI will not reveal."

Indirectly **I2** — no operation accepted by the server is ever silently lost.
Keeping the filter inside the query preserves the gap-free cursor *within a
user's visible set*; filtering after the fact would violate I2 for exactly the
events the user is entitled to.
