# ADR-008: The timeline returns every event, tagged by whether it advanced the state

**Status:** Accepted
**Date:** 2026-08-18
**Decided by:** user (D10 in `docs/PHASE3_PLAN.md`); Claude Code for the ordering
and pagination rules, marked below.

## Context

Plan §7 asks for "the timeline endpoint" in four words and specifies nothing
else — no route, no response shape, no ordering, no scoping rule. The shape is
not obvious, because of one thing the rest of the system has already decided.

**I6 says a losing write in a conflict is never deleted.** ADR-003 goes further:
a genuine conflict changes nothing and asks a human instead of picking a winner,
and the losing operation stays in `referral_event` permanently. The same is true
of `accepted_stale` — an operation that arrived late is recorded and does not
move the state. So `referral_event` is **not** a state history. It is a record of
everything that was submitted, of which only some subset moved the referral.

That leaves a timeline with two ways to lie. Filter to advancing events and it
tells a clean story that omits the fact that two health workers disagreed — the
exact behaviour ADR-003 calls "the behaviour you defend in Chapter 3", made
invisible. Show every event without distinction and the reader sees two events
both claiming `CREATED → IN_TRANSIT` with no way to tell which one counted.

There is a second problem underneath. Whether an event advanced the state is not
a property of the event. It is a property of the event *and everything before
it* — the fold in `replay_state` advances only when an event's `from_state`
matches the state reconstructed so far. Any component that wants to display that
fact has to run the same fold, and if it runs its own copy, the copy will drift
from the one ADR-007's verifier uses. Two derivations of one rule is precisely
the failure I3 exists to prevent, one level up.

Incidentally, `sync_conflict` has been written by `push.py` since P2.1 and read
by nothing. I6 is enforced but not observable.

## Decision

`GET /referrals/{referral_id}/timeline` returns **every** event for the referral
in `seq` order, each carrying an `advanced` boolean, alongside both the cached
`current_state` and the `replayed_state` the fold produces.

The `advanced` flag comes from the **same fold** that verifies I3. `replay_state`
in `server/app/domain/states.py` is refactored to be a thin wrapper over a new
generator, `replay_steps`, which yields the per-event advancement decision as it
folds. `replay_state`'s signature, return type and semantics are unchanged, so
its existing unit tests and both existing callers are untouched. After this
change the condition `frm == state` exists **once in the repository**, and that
is checkable with a grep. The timeline and ADR-007's verifier cannot disagree,
because one is defined in terms of the other.

Scoping follows ADR-005 exactly: the recursive-CTE predicate goes **inside the
lookup query's `WHERE`**, and an empty result is a **404, never a 403**. This is
the fifth call site of `SUBTREE_CTE`. A referral with zero events also returns
404 here, indistinguishable from out-of-scope — deliberate, since distinguishing
them requires a second query whose only function is to leak the difference.
`python -m app.verify_replay` is where that condition is diagnosed instead.

A new response schema lives in `server/app/schemas/referral.py`. `EventOut` in
`server/app/schemas/sync.py` is a frozen contract and is not touched; it is also
the wrong shape, burying `from_state`, `to_state` and `actor_role` inside
`payload`.

**Claude Code's calls within this decision.** Ordering is `seq ASC` — not
`server_time` (two events can share a clock tick), not `device_time`
(client-supplied and arbitrary), and not `lamport` (a partial order, and a losing
write carries a *higher* lamport than the winner it lost to). `seq` is commit
order, and ADR-002's advisory lock is the reason that sentence is true. And the
endpoint does **not** paginate: the fold is prefix-dependent, so a page starting
at event 40 cannot know whether event 40 advanced without having folded 1–39. A
cursor over a fold is only correct if it carries the running state, which is
complexity for no gain on a collection the state machine bounds in practice.

## Alternatives considered

| Option | Why not |
|---|---|
| Return only the events that advanced the state | The clean story, and it deletes the evidence. A conflict becomes invisible, `sync_conflict` stays unreadable, and the one behaviour ADR-003 says is the Chapter 3 centrepiece never reaches a screen. It also answers a question nobody asked — the referral's state history is already one field, `current_state`. |
| Store `advanced` as a column on `referral_event` | A second, persisted source of truth for a fact that is derived from the log — the exact bug I3 exists to prevent, and here the drift would show a health worker the wrong account of what happened. It also needs a migration, which this phase otherwise does not. Cheaper to recompute: the fold is O(events) over an index-ordered read the endpoint is already doing. |
| Compute `advanced` in the endpoint with its own `if frm == state` | Two derivations of one rule. The next change to the conflict policy updates one and silently leaves the other, and the symptom is a timeline that disagrees with the I3 verifier about the same referral. |
| Change `replay_state`'s return type to include the per-event steps | Breaks a pure, heavily unit-tested function and both its existing callers to serve a second consumer's convenience. Wrapping it preserves every existing contract and costs one generator. |
| Reuse `EventOut` from the sync envelope | It is explicitly a frozen API contract, and it is the wrong shape anyway — the three fields a timeline most needs are nested inside `payload`, and it has no place for `advanced`. Widening it would change the pull contract for the benefit of a read endpoint. |
| Paginate with a cursor, like `GET /referrals` | The fold is prefix-dependent; a page is only correct if the cursor carries the running state. That is real complexity to bound a collection the state machine already bounds at roughly six advancing events plus however many losers. |
| Add a `/conflicts` endpoint so `sync_conflict` is readable | That is Phase 6's review queue, and building it here is a feature in a phase plan §7 reserves as buffer. `advanced=false` on this endpoint gives I6 a visible face at zero new surface. |
| Return 403 for a referral outside the subtree | Confirms the referral exists. Same reasoning as ADR-005 — an enumeration oracle over UUIDs the caller was never given. |

## Consequences

**Makes easy.** One request shows the whole story: the log, which events counted,
and the cache agreeing with the replay. That makes the endpoint self-demonstrating
for I3 and gives I6 its first user-visible face without adding any surface. It is
also the natural data source for the Phase 4 referral-detail screen, which
`docs/UI_DESIGN_BRIEF.md` already names.

**A correction this ADR records.** `docs/decisions/ADR-005.md` states the subtree
CTE has three call sites, at the time it was written. D6 added a fourth
(`push.py::_actor_can_see_referral_origin`) and this endpoint is the fifth.
ADR-005 is Accepted and is **not** edited — `ADR-TEMPLATE.md` forbids rewriting a
decided ADR. The correction lives here and in `docs/OBSERVATIONS.md`, and
`scoping.py`'s docstring is changed to *enumerate* its call sites rather than
count them, because a count drifts and a list can be checked.

**Makes hard, and the honest cost.** The response is unbounded in principle. The
state machine bounds it in practice — six advancing transitions plus losers — but
a referral hammered by a misbehaving client could accumulate many non-advancing
events, and this endpoint would return all of them. It cannot be paginated later
without carrying the fold state in the cursor, and that constraint is written into
the endpoint's docstring so it is not discovered by someone adding `?cursor=`.

**A second cost.** `states.py` gains a second public function, and the module's
value is that it is small and quotable. The mitigation is that `replay_steps` is
where the logic now lives and `replay_state` is four lines on top of it, so the
module got one function longer and zero rules longer.

**A third cost, worth stating.** The timeline shows a health worker that their
colleague's action did not take effect. That is honest, and it is the point, but
it is a user-experience question the design brief has not answered — the brief's
banned-words list already forbids showing the word "conflict". Phase 4 owns the
wording; this ADR only guarantees the data is available to be worded well.

**How the benefit is measured.** Two tests. An integration test pins the demo
walk's exact shape — 8 events, 6 with `advanced=true`, the conflict event with
`advanced=false` **and** a `sync_conflict` row carrying the same `op_id`. And a
grep that `frm == state` appears exactly once under `server/app/`, which is what
makes "the timeline and the verifier use one fold" a checkable claim rather than
an intention.

## Which invariant this protects

**I3** — the timeline reports `current_state` and `replayed_state` side by side
and derives `advanced` from the same fold the I3 verifier uses, so the endpoint
cannot show a state history that disagrees with the log.

**I6** — a losing write is never deleted. Before this endpoint, that invariant was
enforced in the database and observable nowhere. `advanced=false` is what makes
it visible.
