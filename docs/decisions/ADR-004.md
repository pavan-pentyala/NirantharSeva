# ADR-004: One generic pull envelope with a typed payload, and one shared event sequence behind it

**Status:** Accepted
**Date:** 2026-08-17
**Decided by:** user (D3 in `docs/PHASE2_PLAN.md`); the shared-sequence part is a
consequence of D3 that D3 did not spell out — see "The part D3 did not say".

## Context

`GET /sync/pull` currently returns toy-shaped events: `toy_id`, `old_value`,
`new_value`, flat at the top level of each event. That shape was written in P1.1
when the toy model was the only entity that existed, and the contract was frozen
at that point.

Phase 2 introduces `referral_event`, whose type-specific fields are completely
different — `from_state`, `to_state`, `actor_role`, `actor_user_id`. Decision D1
keeps the toy model alive and frozen until Phase 4, because Phase 1's three fault
tests are experiment E4's evidence and two of them are Playwright tests that need
a screen to click, which referrals will not have until P4. So for two phases,
**one cursor has to carry two entity types with disjoint field sets**, and in P6
a third one arrives when patient events start syncing.

The constraint that makes this non-obvious is the review calendar. Re-cutting the
pull contract costs a client change plus a re-run of both Playwright fault tests
every time it happens. Doing it now costs that once, while there is exactly one
client and the tests are freshly green. Doing it at P6 costs it again, on top of a
PWA, a service worker, and a real referral UI.

## Decision

**One event shape for every entity type.** Fields the sync engine itself needs
stay flat; everything the sync engine does not understand moves into `payload`,
discriminated by `entity_type`. This mirrors the push `Op` contract, which has
carried a generic `payload: dict` since P1.1 — push and pull now have the same
shape on both sides of the wire.

```json
{
  "seq": 1183,
  "entity_type": "referral",
  "entity_id": "<uuid>",
  "op_id": "<uuid>",
  "device_id": "d-1",
  "lamport": 17,
  "device_time": "2026-08-10T09:00:00Z",
  "server_time": "2026-08-10T09:00:03Z",
  "payload": {
    "from_state": "CREATED",
    "to_state": "IN_TRANSIT",
    "actor_role": "ASHA",
    "actor_user_id": "<uuid>"
  }
}
```

The dividing line is not arbitrary and is worth stating precisely: **a field is
flat if the sync engine reads it, and in `payload` if only the domain reads it.**
`seq` drives the cursor, `lamport` and `device_id` drive conflict resolution,
`op_id` drives idempotence, `entity_type` and `entity_id` route the event to a
cache table. Nothing else is the engine's business. `to_state` is the domain's.
That rule is what stops `payload` from slowly refilling with flat fields as
entity types are added.

Toy events pass through the same envelope: `entity_type: "toy"`, with
`{"old_value": …, "new_value": …}` in `payload`. This is a deliberate breaking
change to a frozen contract, and it lands in a single commit together with
`client/src/api/client.ts` and `client/src/sync/engine.ts`. **The two Playwright
fault tests passing afterwards is the regression check** that the toy path still
works through the new envelope — that is what makes this change safe to make at
all, and the reason for making it now rather than at P6.

### The part D3 did not say: the two tables must share one sequence

D3 says one cursor serves both entity types. That is not implementable as
written, and the reason is worth recording because it is invisible until it
corrupts a client's cursor.

`toy_event.seq` and `referral_event.seq` are each `BIGSERIAL`, so each has its own
independent Postgres sequence. Both would start near 1 and hand out overlapping
numbers. A single cursor over a `UNION` of the two tables then breaks in two ways:
`WHERE seq > :since` drops rows from one table because the other has already
pushed the cursor past them, and the client's monotone-cursor assumption — which
ADR-002 went to some trouble to earn — no longer holds.

**Decided: both event tables draw `seq` from one shared Postgres sequence.**
Migration `0003` creates `event_seq`, starts it above the current
`max(toy_event.seq)` so existing rows keep valid and still-monotone numbers, and
points both tables' defaults at it. `0002` is not edited (handoff §6); `0003`
issues an `ALTER TABLE toy_event ALTER COLUMN seq SET DEFAULT nextval('event_seq')`.

This composes exactly with ADR-002. That advisory lock is a single global key
(`4711`) held across every event append of any type, so a shared sequence is
handed out under the same serialisation that already makes seq order equal commit
order. One lock, one sequence, one cursor, one gap-free stream — the three
decisions only work as a set.

## Alternatives considered

| Option | Why not |
|---|---|
| Keep the flat toy shape and add nullable referral columns beside it | Every event carries every entity type's fields, all but one set null. Adds patient columns at P6 and never removes any. The client cannot tell which nulls are meaningful, and the response body grows with the number of entity types the reader does not care about. |
| A separate endpoint per entity type — `/sync/pull/toy`, `/sync/pull/referral` | Multiplies the cursor: the client now maintains one per type and each is a separate round trip on a connection that may only be up for seconds. It also loses the global ordering between types, which P6 needs — a patient-merge event and a referral event on that patient must be applied in the order the server committed them. |
| Top-level union type, discriminated on the wire but flat in each branch | Roughly the same client-side ergonomics as the payload version, but the server serialiser and the OpenAPI schema both get a branch per entity type, and the flat/nested boundary stops being a rule anyone can state. Adding an entity type touches the envelope instead of only the payload. |
| Defer the change to P6, when patient events actually force it | This is the alternative that was genuinely tempting and it loses on cost, not principle. At P6 the same change must be made against a PWA with a service worker and cached responses, a real referral UI, and Playwright tests that by then cover more than the toy. Today the client is one file and two tests. Same change, several times the blast radius, and the intervening phases would all have been built against a shape known to be wrong. |
| Composite cursor `(table, seq)` instead of a shared sequence | Keeps two sequences but pushes the interleaving problem into the client, which must now merge two ordered streams and reason about which is behind. More client state, more to get wrong offline, and it still cannot produce a single global order across types. |

## Consequences

**Makes easy.** Adding an entity type at P6 is a new `payload` shape and a new
branch in the client's apply switch. No migration to the contract, no client
version negotiation, no re-cut. The pull response is also self-describing —
`entity_type` says what the payload is — which makes a captured response readable
in the report appendix without a schema alongside it.

**Makes hard, and the honest cost.** The client loses static typing at the point
it needs it most. `payload` arrives as `Record<string, unknown>`, so
`client/src/sync/engine.ts` must narrow on `entity_type` before it can touch a
field, and TypeScript cannot check that the narrowing matches what the server
actually sends. A discriminated union with a type guard per entity type recovers
most of this, but the guard is hand-written and can drift from the Pydantic model
on the server. Nothing detects that drift automatically; the integration tests
are the only thing standing between a renamed payload field and a client that
silently applies nothing.

**A second cost.** `/sync/pull` now reads from two tables and will read from three
at P6. It is a `UNION ALL` ordered by `seq` with a `LIMIT`, and Postgres must sort
the union before it can page it. At Phase 2 volumes this is irrelevant. It is
worth naming because the P2.2 org-scoping filter has to be applied to **every
branch of that union independently** — a scoping predicate applied to the outer
query only, or to one branch only, is exactly the data leak plan §6.4 warns
about, and it is easier to write by accident once the query has more than one
`FROM`.

**A third cost, stated because it is irreversible.** The shared sequence means the
two event tables are no longer independent. Dropping `toy_event` at P4 must not
drop or reset `event_seq`, or every client cursor in existence points into the
future and those clients silently stop receiving events. The P4 drop migration
has to leave the sequence standing.

**How the benefit is measured.** There is no experiment number for this one. The
evidence is negative and will be visible in the P6 diff: adding patient events
should touch `payload` handling and nothing in the envelope, the cursor, or the
client's sync engine. If P6 has to change `EventOut` again, this decision did not
pay for itself and the ADR should be superseded saying so.

## Which invariant this protects

- **I2** — no operation accepted by the server is ever silently lost. The shared
  sequence is what keeps the single cursor gap-free across entity types; without
  it, a client's cursor skips events in the other table and never asks again.
  This is the same failure ADR-002 prevents within one table, at the boundary
  between two.

Otherwise this is a convenience decision: the envelope shape itself protects no
invariant, it buys the ability to add entity types without re-cutting a contract
the client depends on.
