# ADR-002: Event appends are serialised with a transaction-scoped advisory lock

**Status:** Accepted
**Date:** 2026-08-16
**Decided by:** user (mandated by `docs/IMPLEMENTATION_PLAN.md` §3.2)

## Context

Clients pull changes with `GET /sync/pull?since=<cursor>`, where the cursor is
`referral_event.seq`, a `BIGSERIAL`. The client applies the events it receives,
advances its cursor to the highest `seq` it saw, and never asks for anything
below that number again.

This is only safe if sequence order equals commit order, and by default it does
not. Postgres allocates a sequence value when the row is inserted, **not** when
the transaction commits. So:

1. Transaction A inserts an event and is allocated `seq = 100`. It is still open.
2. Transaction B inserts an event, is allocated `seq = 101`, and commits.
3. A client pulls `since=99`, sees only event 101, and advances its cursor to 101.
4. Transaction A commits. Event 100 is now visible — but that client will never
   ask for it again.

The event is lost to that client permanently, which violates I2. The failure is
worse than it looks: it needs a specific interleaving of concurrent writes, so it
passes every test written against a single writer, and appears in production-like
conditions as a referral that one device simply never learns about.

## Decision

Every event append takes a transaction-scoped advisory lock before inserting:

```python
SEQ_LOCK = 4711  # arbitrary constant, documented here

async def acquire_seq_lock(session) -> None:
    await session.execute(text("SELECT pg_advisory_xact_lock(:k)"), {"k": SEQ_LOCK})
```

The lock is held until the transaction commits or rolls back — Postgres releases
`_xact_` locks automatically, so there is no unlock path to forget. Because no
second appender can allocate a sequence value while the first holds the lock,
sequence order is commit order, and a gap-free scan of `seq` is safe.

The lock key is **global, not per-referral**. This is deliberate: the pull cursor
is a single global sequence, so the ordering guarantee has to be global too. A
per-referral key would allow more parallelism and would not fix the bug.

## Alternatives considered

| Option | Why not |
|---|---|
| Order the pull by `server_time` instead of `seq` | Identical problem — the timestamp is also taken before commit. It is additionally not unique, and under `CLOCK_MODE=simulated` (ADR-001) many events share one timestamp exactly. |
| Let the client tolerate gaps: re-pull a trailing window and deduplicate by `op_id` | Pushes correctness onto every client, and the window size is a guess. Worse, a gap is ambiguous — the client cannot tell "committing right now" from "rolled back and will never exist", so it must re-scan forever or accept loss. |
| `SERIALIZABLE` isolation on the appending transaction | Does not address this. Serialisable prevents anomalies in what transactions *read*; it says nothing about the order in which `BIGSERIAL` values are handed out relative to commits. It would also add serialisation-failure retry handling for no benefit here. |
| A trigger that assigns the sequence at commit time | Postgres has no true at-commit trigger. `AFTER` triggers still fire inside the transaction, before commit, so the race is unchanged. |
| Track a low-water mark: expose the oldest in-flight transaction id (`pg_snapshot_xmin`) and never let a client's cursor advance past it | This is the correct answer at scale, and is essentially what Postgres logical replication does. Rejected on cost, not correctness: it is materially more code and more subtle reasoning than a single-node project of this size justifies, and it is harder to defend in a twenty-minute review than one line of SQL. **This is the answer to "what would you do at scale?"** |

## Consequences

**Makes easy.** The pull cursor is a simple monotonic integer with no gaps, so
the client sync engine needs no windowing, no deduplication pass, and no
low-water-mark tracking. A large part of Phase 1.2's simplicity is bought here.

**Makes hard, and the honest cost.** Every event append across the whole system
serialises behind one lock. Write throughput is therefore bounded by one append
at a time, regardless of how many API workers are running. At this project's
scale — a single node, tens of devices, batched pushes — that is not a limit
anyone will reach, but it is a real ceiling and it should be stated rather than
discovered.

A second cost: the lock is taken inside the same transaction as the receipt write
and the effect (I1, plan §5.3), so **the lock is held for the duration of the
whole operation**, not just the insert. Any slow work added to that transaction
later becomes a system-wide write stall. Keep that transaction small.

**How the cost is measured.** Experiment E5 reports the sequencing lock's effect
on p95 write latency, by running the load test with and without it. The intended
Chapter 4 sentence is: *"the sequencing lock adds X ms to p95 write latency,
accepted in exchange for a gap-free pull cursor."* A measured cost is a defence;
an unmeasured one is a hole.

## Which invariant this protects

**I2** — no operation accepted by the server is ever silently lost.

Indirectly **I3**: replaying the event log only reconstructs `current_state`
correctly if the log can be read in a complete, ordered scan.
