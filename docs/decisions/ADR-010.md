# ADR-010: The pull payload carries a referral snapshot, not just its transition

**Status:** Accepted
**Date:** 2026-08-19
**Decided by:** user (D14 in `docs/PHASE4_PLAN.md`).

## Context

`GET /sync/pull`'s referral branch (`server/app/sync/pull.py`) packs
`from_state`, `to_state`, `actor_role`, `actor_user_id` into each event's
`payload` — everything the sync engine and the I3 fold need, and nothing else,
by design (D3/ADR-004: "fields the sync engine itself reads stay flat;
everything only the domain reads is in `payload`").

Phase 4's screens need more than that to render. Screen 1's list row shows the
patient's name, age/sex, the reason, and which facility the referral is headed
to. None of that is in the event stream today, and there is no other channel:
`referral_cache` in Dexie is built entirely by folding pulled events
(`client/src/sync/engine.ts`'s `applyPulledEvents`), the same pattern the toy
model already uses. A referral event that cannot describe the referral leaves
the client with a state machine and nothing to show next to it.

## Decision

The referral branch's `payload` gains `patient_name`, `age`, `sex`, `reason`,
`priority`, and `target_org_name` — joined in from `patient` and `org_unit`
inside the same subquery, before `LIMIT`, the same place the existing subtree
predicate already lives (`pull.py`'s own docstring warns against filtering
after the fetch; the same rule applies to joining after the fetch, for the
same reason — a page that runs out of rows in Python still has to report a
correct `cursor`/`has_more`).

`applyPulledEvents` in `engine.ts` gains a `referral` branch alongside the
existing `toy` one: it folds `advanced` using the same left-to-right rule
`replay_steps` encodes server-side (D10/ADR-008), and only a step where
`advanced` is true writes into `referral_cache`. A losing or stale event still
lands in the outbox record's status update, but does not overwrite the cache
— the client-side mirror of what the server's own fold already decided.

ADR-004's envelope shape is unchanged: `seq`, `entity_type`, `entity_id`,
`op_id`, `device_id`, `lamport`, `device_time`, `server_time` stay flat, and
`payload` stays the one place a domain packs whatever it needs. This is
payload growth within the shape ADR-004 defined, not a new field on the
envelope and not a new endpoint.

## Alternatives considered

| Option | Why not |
|---|---|
| A separate `GET /sync/bootstrap` snapshot endpoint, pull stays delta-only | Two sources of truth on the client — a snapshot fetched once and a delta stream applied continuously — with a consistency window between them that has to be reasoned about on every reconnect. The whole point of D3's single seq-ordered stream was to avoid exactly this. |
| Client calls `GET /referrals`/`GET /referrals/{id}` to hydrate names when online | Those endpoints return `patient_id`, not a name (`ReferralOut` in `server/app/schemas/referral.py`) — still not enough to render Screen 1 without a further change, and it reintroduces an online-only code path onto a UI whose entire premise (plan §8.3, brief §8) is that it reads only from the local cache and looks identical offline. |
| Only widen payload for `create_referral`-type events, leave `transition` events thin | The cache would then only have patient details for referrals whose creation event happened to still be within the client's pull window; any referral synced from a point after its creation (a second device, a first login) would show state changes with no patient to attach them to. Simpler to put the join in the query once for the whole branch than to reason about which events need it. |

## Consequences

**Makes easy.** `referral_cache` becomes self-sufficient — a screen renders
from one Dexie table, online or offline, with no second round trip. This is
the same shape `toy_cache` already proved out in Phase 1.

**Makes hard, and the honest cost.** Every referral event is now a fatter row
on the wire — a `transition` event repeats `patient_name`/`reason` it already
sent on the `create_referral` event for the same referral, because the stream
is append-only and a consumer cannot look backward for context it dropped. At
demo scale (single digits to low hundreds of referrals) this is not
measurable; at Phase 7's cohort-generator scale it is a real cost this ADR
accepts without measuring, because Phase 4 has no load target to measure
against yet — E5 (`docs/IMPLEMENTATION_PLAN.md` §13) is where payload size
under load gets a number.

**A second cost.** `target_org_name` denormalizes an org name into an event
payload at the moment it was written; if an org is later renamed, historical
events keep the old name. This is arguably correct for a timeline (it shows
what the sender saw at the time) and is the same trade-off `referral_event`
already makes by storing `actor_role` rather than joining it live.

**How the benefit is measured.** An integration test pulls a referral's events
after `create_referral` and asserts `patient_name`/`reason` are present and
correct in the payload. A client-side test asserts `applyPulledEvents` only
updates `referral_cache` on an `advanced=true` step, using a fixture with one
conflict pair (the demo walk's own conflict, D12) to prove the losing event is
received but not applied.

## Which invariant this protects

**I3** — the client-side fold that builds `referral_cache` uses the identical
advancement rule the server's `replay_steps` uses, so the two cannot disagree
about which pulled event counted.

None of I1, I2, I4–I7 are touched; this is a read-path payload change.
