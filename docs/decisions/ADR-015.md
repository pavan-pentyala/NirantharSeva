# ADR-015: A generated cohort is loaded by replaying it through `/sync/push`

**Status:** Accepted
**Date:** 2026-08-21
**Decided by:** user (D28 in `docs/PHASE7_PLAN.md`).

## Context

`docs/IMPLEMENTATION_PLAN.md` §11.1 says the generator emits
`patients.csv`, `referrals.csv`, `events.csv` and
`ground_truth_identity.json`, and that every run must be reproducible from
that directory alone (I7). §13.1 says each experiment cell begins "fresh
database, **load cohort**, install `SimulatedClock`, run the timeline". The
plan never says how the cohort gets from those CSVs into the database, and
the answer decides what the experiments in Chapter 4 are actually
measurements *of*.

The tempting answer is a bulk `INSERT`. A cohort is a few thousand rows of
known shape; `generator/gold_set.py` already writes patients that way and
it takes milliseconds. Phase 8 runs E1 at eighteen cells times three seeds,
so load time is multiplied fifty-four times over before E2–E6 are counted.

What makes it the wrong answer is what those rows are. A `referral_event`
row is not free-standing data — it carries a `lamport` value that has to be
consistent with its siblings, a `seq` whose ordering must equal commit
order (ADR-002's advisory lock is the only thing that guarantees this), and
an `op_id` that a `sync_receipt` row must agree with (I1). `referral.current_state`
is a cache whose truth is the fold of those events (I3). A bulk loader that
writes them directly is a second implementation of every one of those
guarantees, sitting beside `app/sync/push.py`, with no test forcing the two
to agree — and the failure mode is not a crash. It is an experiment result
that looks fine.

## Decision

The generator writes CSVs and nothing else. `server/scripts/load_cohort.py`
reads them and replays them through the running API: `create_referral` and
`transition` operations posted to `/sync/push`, one authenticated session
per generated ASHA, in the order `events.csv` gives.

The district is the exception, and it is an exception of capability rather
than principle: there is no endpoint that creates an `org_unit` or an
`app_user`, so those rows are inserted directly, exactly as `app/seed.py`
already does. This ADR does not authorise adding such an endpoint — that
would be an auth-surface change and belongs behind its own question.

The loader takes an `upto_device_time` parameter it does not itself need.
Phase 8's runner advances a `SimulatedClock` in steps and must push only
the events that have "happened" by each step; building that seam now costs
one argument, and retrofitting it later means editing the loader while
experiments are running against it.

## Alternatives considered

| Option | Why not |
|---|---|
| Bulk `INSERT` into `referral` and `referral_event` | Fastest by a wide margin, and genuinely tempting at fifty-four loads. Rejected because it reimplements lamport assignment, `seq` ordering, receipt claiming and the `current_state` fold — the four things Phases 1–3 exist to get right — in a second place that no test compares against the first. It also makes E4 (fault injection) and E6 (full-cohort) measurements of a code path no device ever takes, which is the specific criticism a panel is most entitled to make of a synthetic evaluation. |
| Direct SQL for patients and the district, `/sync/push` for referrals and events | A real middle ground, and it keeps the event log honest. Rejected because patients created by SQL skip `_resolve_patient` entirely, so `duplicate_rate` — the knob E3's whole precision/recall table is built on — would never reach the matcher. ADR-009 put the patient inline in `create_referral` precisely so that creating a referral is what creates a patient; loading a cohort any other way tests a different system. |
| Generate ops directly and call `handle_push()` in-process, skipping HTTP | Faster than HTTP, and still exercises I1 and ADR-002 honestly, since `handle_push` is where they live. Rejected as the default because it bypasses authentication and therefore ADR-006's actor resolution — the loader would construct its own `Actor` objects, and "every referral originates in its own ASHA's village" would become an assertion about the loader's own bookkeeping rather than about the system. Worth revisiting *only* if the measured load time in P7.1 makes Phase 8 infeasible, and worth saying out loud if it is. |
| Snapshot a loaded database and restore it per cell (`pg_dump`/`pg_restore`) | Load once, restore fifty-four times — the fastest option that still produces a real event log, because the log was produced for real, once. Rejected for this project because each E1 cell varies `dropout_rate`, so the cohorts genuinely differ and there is no single snapshot to restore; it would help only for repeated seeds of an identical cell. Recorded because it is the right answer if Phase 8's runtime turns out to be the binding constraint on a re-run. |

## Consequences

**Makes easy.** Every experiment result describes the same code path a real
device drives. E4's fault claims and E6's full-cohort numbers mean what they
say. `python -m app.verify_replay` over a freshly loaded cohort becomes a
real end-to-end check of I3 at scale — several hundred referrals, all of
them written by the production path — which is a stronger statement than any
unit test in the repository makes.

**Makes hard, and the honest cost.** Loading is now bounded by HTTP and by
one transaction per op (I1's rule, deliberately not batched), so it is
orders of magnitude slower than an `INSERT`. D31 sets the default cohort at
~200 patients partly for this reason. **P7.1 is required to measure one real
load and report the number**, because if fifty-four of them do not fit in a
sensible Phase 8 window, the right response is to change the plan then —
using the in-process or snapshot alternatives above — and not to discover it
in week nine.

**A second cost.** The loader needs credentials for every generated ASHA, so
`users.csv` and the district-creation step have to run before any referral is
pushed, and the loader holds a live token per ASHA. That is more moving parts
than an `INSERT`, and it is a real place for a cohort load to fail halfway.
The loader should therefore be re-runnable against a partially loaded
cohort — which it gets nearly for free, because `op_id`s are derived
deterministically from the cohort and I1 makes a replayed push a no-op.

**A third cost.** The generator and the loader are now coupled through the
CSV schema, in two different directories (`generator/` and
`server/scripts/`). They are kept adjacent in review by that schema being
written down in `docs/PHASE7_PLAN.md` rather than living only in code.

**How the benefit is measured.** Not as a benefit — this is fidelity bought
with time. What is verified is that the fidelity is real: `verify_replay`
clean after a full load, zero `ESCALATED` events present before the first
sweep runs, and every referral's `origin_org_id` equal to its own ASHA's
village.

## Which invariant this protects

**I1 and I3, by not writing a second implementation of them.** The receipt
-and-effect transaction and the event-log-is-truth rule are enforced in
exactly one place, `app/sync/push.py`, and this decision keeps it that way
for experimental data as well as production data.

It also protects **ADR-002**'s sequence ordering (the advisory lock is taken
by the real push path and would have to be re-derived by a bulk loader) and
**ADR-006**'s server-side actor resolution (the loader authenticates rather
than asserting identity).
