# ADR-013: The identity merge decision is a plain REST call, not a sync operation

**Status:** Accepted
**Date:** 2026-08-20
**Decided by:** user (D25 in `docs/PHASE6_PLAN.md`).

## Context

Every write in this system goes through `/sync/push`: an op is appended to
the client's Dexie outbox, flushed when there is signal, and applied
server-side inside I1's receipt-and-effect transaction. That uniformity is
the architecture — it is what makes the client offline-first, what makes
retries safe, and what the whole of Phase 1 exists to establish.

Phase 6 adds a write that does not fit it. The ANM's answer to "is this the
same person?" merges two patient records, repoints every referral attached
to one of them, and is not reversible from any screen. The design bundle
states the stakes twice, unprompted: *"a wrong merge is worse than a slow
one"*, and *"two large, unambiguous decisions — no middle option"*.

The constraint that makes this non-obvious is that the outbox's greatest
strength is exactly wrong here. The outbox exists so a decision made with
no signal still lands later. A merge decision made with no signal is a
decision made against a pair that may already have been decided by someone
else, or whose underlying records may have changed — and it lands anyway,
silently, on reconnect.

## Decision

The review queue is read with `GET /identity/reviews` and answered with
`POST /identity/reviews/{id}/decide`, both ordinary authenticated
JSON endpoints requiring a live connection. Neither goes through the
outbox, and no new op type is added to the frozen `/sync/push` contract.

Deciding is idempotent by a conditional update rather than by a receipt:
`UPDATE identity_review SET status = :decision, decided_by = :user,
decided_at = :now WHERE id = :id AND status = 'pending' RETURNING id`. If
it returns nothing the pair was already decided, and the endpoint returns
the stored outcome with `200` rather than an error — a double-tap on a
tablet is harmless, and a nurse who taps twice should not see a failure for
having done nothing wrong.

Screen 6 is disabled, with an explicit "needs a connection" message, when
the device is offline. It is the only screen in the project that says that,
and it says it deliberately.

## Alternatives considered

| Option | Why not |
|---|---|
| A new `entity="identity_review", operation="decide"` op through `/sync/push` | Architecturally consistent, offline-capable, and gets I1's exactly-once handling for free — genuinely the tempting answer. Rejected because it makes the dangerous thing easy: a merge queued offline is applied on reconnect against whatever the pair looks like *then*, with no chance for the nurse to see that it changed. The op would land "correctly" and merge the wrong people. Idempotency is not the property this write needs; recency is. |
| Keep the endpoint online-only but still route it through the outbox for uniformity | The worst of both — outbox machinery, ordering and retry semantics to maintain, with the offline capability that machinery exists for deliberately disabled. Uniformity for its own sake, paid for in code nobody benefits from. |
| Allow offline decisions but re-validate the pair server-side on arrival and reject if it changed | Sound in principle. Rejected because "reject if it changed" surfaces as a failure the nurse sees hours later, detached from the decision she made, with no way to redo it from the queue (the pair is gone from her cached view). A conflict she cannot act on is worse than a screen that told her upfront it needed signal. |
| Merge via a supervisor-only admin path instead of the ANM's queue | Moves the decision to someone with a desk and a connection, which solves the staleness problem by relocating it. Rejected because `docs/DOMAIN_PRIMER.md` assigns the review queue to the ANM explicitly — she is the person who knows the two villages and the families, and the supervisor is not. |

## Consequences

**Makes easy.** The nurse always decides against the current state of the
pair. The `/sync/push` contract stays frozen and gains no entity type.
There is no offline merge path to reason about, test, or explain — the
failure mode simply does not exist rather than being handled.

**Makes hard, and the honest cost.** This is now the one screen in a
project whose entire premise is offline-first that requires a connection,
and that is a real inconsistency a panel is entitled to ask about. The
answer is that offline-first is a means, not an end: it exists so that an
ASHA in a village with no signal never loses a patient's referral. The ANM
sits at a sub-centre, reviewing a queue that is by nature a batch of
already-recorded work, and the cost of her waiting for signal is a delay,
while the cost of her deciding blind is a wrong merge. The two are not
comparable.

**A second cost.** Two write paths now exist, and a future change could
route something through the wrong one without any test noticing. The
mitigation is narrowness: this ADR authorises exactly two endpoints under
`/identity/`, and nothing else in the project may take the same exemption
without its own ADR.

**A third cost.** Because the decision does not flow through
`/sync/pull`, other devices do not learn of a merge through the sync
stream. A referral that was repointed to a different patient shows its new
patient's name only after that referral's next pulled event, or a refetch.
No screen currently displays a patient identity that a merge would
invalidate mid-session, so this is latent rather than visible — but it is
the thing that breaks first if a patient-detail screen is ever added.

**How the benefit is measured.** Not measured as a benefit — this is a
capability deliberately given up. What is verified is the containment: a
P6.2 test asserts a second identical `decide` POST returns the same outcome
without changing anything, and no test anywhere pushes an identity
decision through `/sync/push`.

## Which invariant this protects

None of I1–I7 directly. I1 is about receipt-and-effect atomicity for
*synced* operations, and this write is deliberately outside that system;
the conditional `UPDATE ... WHERE status = 'pending'` gives it the same
decide-once property by a different and simpler mechanism.

It protects **ADR-005's scoping rule** the same way every other endpoint
does: both new routes filter through `SUBTREE_CTE` in SQL, so an ANM can
only see and decide pairs inside her own sub-centre.
