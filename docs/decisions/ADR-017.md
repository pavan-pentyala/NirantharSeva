# ADR-017: E1 reports measured detection and modelled recovery as two separate results

**Status:** Accepted
**Date:** 2026-08-23
**Decided by:** user (D34)

## Context

E1 is the headline experiment: *escalation {on, off} × dropout {10, 25,
40}%*, reporting loop closure rate. It is the number the report is built
around and the one a panel will push hardest on.

There is a hole under it, and it is better found now than in the viva.

**Escalation, in this system, surfaces a stalled referral. It does not move
it.** `app/domain/escalation.py`'s sweep finds referrals past their SLA,
writes an `escalation` row and a `SYSTEM`-authored `ESCALATED` event, and
`NOTIFY`s the dashboard. What happens next is a supervisor reading Screen 4
and telephoning an ASHA — a human act, outside the software, deliberately
so (`docs/DOMAIN_PRIMER.md`; the frozen scope list rules out SMS/IVR, which
is what an automated nudge would have required).

The generator models drop-out as a referral whose timeline simply stops
(`generator/timeline.py`, per-stage `dropout_rate`). Nothing in the
generator, the loader, or the server ever resumes a stopped timeline.

So if E1 is run exactly as §13.2 specifies, **the escalation-on and
escalation-off arms produce identical loop closure rates**, because closure
is decided entirely by the generated timeline and escalation cannot touch
it. The headline result would be "escalation has no effect", produced by a
harness that was never capable of showing any other answer. That is not a
null result; it is an unasked question.

## Decision

**E1 reports two families of number, presented separately and never
combined into one figure.**

**1. Measured — what the code actually did.** Escalation's *detection*
performance, over the same escalation-on × dropout grid:

- detection rate: of the referrals that dropped out, the fraction the sweep
  raised an escalation for;
- time-to-detection: hours of simulated time between a referral's last real
  event and its `ESCALATED` event;
- escalation volume: escalations raised per hundred referrals, including
  those raised against referrals that had *not* dropped out (the false
  positives that E2's alert-fatigue frontier then trades against).

Every one of these is a property of code that ran. No assumption enters.

**2. Modelled — closure under an assumed responsiveness.** A new cell
parameter, `escalation_response_rate` (`r`), swept over
**{0, 0.25, 0.5, 0.75}**. When the sweep escalates a referral, the runner
draws once against the cell's seeded RNG; with probability `r` that referral
**resumes its interrupted timeline** after a response delay, and with
probability `1 − r` it stays dropped. Loop closure rate is then reported as
a function of `r`, and every table and figure carries the assumption in its
caption.

The resumption is pushed through the real `/sync/push` as an ordinary
transition authored by the original actor — not a direct state write —
for the same reason ADR-015 gives for the cohort load itself: a second
path into `referral_event` is a path no real user takes, and it is free to
drift from the one they do.

**`r` is an axis, not a constant.** The result E1 reports is not "escalation
improves closure by X%" but "escalation improves closure by X% *if
supervisors act on a quarter of alerts*, by Y% *if they act on half*" — a
frontier, with the reader able to locate their own field reality on it.
The interesting sentence Chapter 4 can then defend is the break-even one:
the responsiveness below which escalation costs more attention than it
returns.

### The r = 0 identity check, which is free and worth stating

Escalation-on with `r = 0` must produce **exactly** the closure rate of the
escalation-off arm at the same dropout level and seed. Raising an alert
nobody acts on cannot close a loop.

That gives the harness an internal validity check that costs nothing to run
and is hard to satisfy by accident: if those two cells disagree, the harness
is contaminating its own measurement — most likely leaking state between
cells, which is exactly the failure ADR-016 exists to prevent. It is
asserted in P8.1's exit criteria rather than merely observed.

## Alternatives considered

| Option | Why not |
|---|---|
| Pick one plausible response rate, report a single closure-rate improvement | The strongest-sounding headline and the least defensible one. Every number in Chapter 4 would rest on one invented constant, and the honest answer to "where does 0.5 come from?" is "nowhere" — which discredits the measured results sitting next to it, not just the modelled one. |
| Report detection only; make no closure claim at all | Completely safe and genuinely tempting: it is all measurement, no assumption. Rejected because it silently discards the question the project was posed to answer — whether referral continuity tooling closes loops — and a panel asking "so does it help?" would get "we can tell you we noticed" as the entire answer. The sweep gives the same safety, plus a conditional answer. |
| Derive a response rate from published health-systems literature and cite it | Sounds rigorous; is worse. There is no dataset behind this cohort — the patients, villages and drop-outs are all synthetic — so a citation-backed constant applied to invented data lends borrowed authority to a number that cannot inherit it. A clearly-labelled swept assumption is the more honest instrument, and says so out loud. |
| Model the supervisor's response inside the application instead of the harness | An auto-resume on escalation would make the software do something real health systems do by phone, changing what the system *is* in order to make an experiment easier to run. It would also invalidate every earlier phase's demo, and it edits frozen code in the week §13 declares it frozen. |
| Sweep `r` continuously rather than at four points | Four points across the plausible range, at three seeds each, is already 45 E1 runs. A finer grid buys smoothness in a figure whose x-axis is an assumption anyway — precision that would imply more knowledge than exists. |

## Consequences

**Makes easy.** The measured half is unattackable: it reports what ran. The
modelled half states its assumption in its own axis label, so the obvious
panel question ("how do you know supervisors respond?") is already answered
by the figure — the answer is "we don't, so here is the whole range." A
reader who thinks real responsiveness is 10% can read their own number off
the curve instead of discarding the result.

**Makes hard, and the honest cost.** E1 grows from 6 cells to 15 (3
escalation-off + 3 dropout × 4 response rates), so 45 runs at three seeds
rather than 18. On P7.1's measured ~38s load that is roughly half an hour
of cohort loading; ADR-016's in-process transport should improve on it, and
P8.1 must re-measure rather than assume.

**A second cost, and it is the real one.** The report can no longer say
"escalation improves loop closure by X%" without a conditional clause. That
sentence would have been the cleanest line in Chapter 4. It would also have
been unsupported, and the clause is the difference between a finding and a
claim.

**A third cost.** `escalation_response_rate` does not correspond to
anything in the shipped system — no column, no config key the application
reads, no code path. It exists only in the harness. That gap must be stated
plainly wherever the parameter appears, or a later reader will go looking
for the feature that implements it.

## Which invariant this protects

**I7** — every experiment result reproducible from a seed and a config
file. The response draw is the only stochastic element in Phase 8 that does
not come from the generator, so it must be drawn from the cell's own seeded
RNG and its seed recorded in the cell's resolved config. A response modelled
with an unseeded `random()` would make E1 unreproducible while leaving every
other reproducibility check in the phase passing.
